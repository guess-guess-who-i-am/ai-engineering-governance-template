# 用户故事与测试追踪

## 目录

1. 故事结构
2. 验收条件
3. 测试映射

5. 执行记录与协作
6. 生命周期

## 1. 故事结构

使用 `requirements/user-stories/TEMPLATE.md`。Actor 是真实使用者或系统消费者；Need 是动作和结果；Value 说明为何值得实现。不要把组件名、数据库表或实现方案写成用户价值。

## 2. 验收条件

每条 AC 只表达一个可观察承诺：

- happy：主成功路径。
- failure：可预期失败和稳定错误语义。
- boundary：空值、上限、重复、并发、超时或生命周期边界。
- security：身份、权限、隐私和滥用路径。
- performance：具名指标、环境和阈值。
- accessibility：键盘、焦点、语义、对比度或动态效果。

高风险故事至少包含一个非 happy 条件。Given 不隐藏无法建立的环境；Then 不写“正常工作”之类不可证伪描述。

## 3. 测试映射

一条 AC 可以映射到多个测试层：

```text
AC-001 -> unit rule + integration persistence + browser journey
AC-002 -> contract error shape + authorization E2E
```

选择最小稳定层证明每个事实，再用少量 E2E 证明连接关系。verified 故事的映射必须包含实际存在的 `file=` 路径。

## 4. 轻量测试设计重点

每个 Story 只保留三个通用决定：主成功路径、最重要的失败与恢复、变更影响面。主成功路径引用真实 AC；高风险和关键风险 Story 必须引用一个非 happy AC；低中风险确实没有相关失败时可以写具体 N/A。变更影响面用一句话指出直接变化、相邻消费者和真正需要回归的表面。

性能、安全、可访问性、兼容性、部署、数据质量和供应链属于项目级类别，由 `quality/gates.json` 一次性决定。只有 Story 真正引入相应风险时才增加对应 AC。不要把风险检查表变成每个 Story 的七项 N/A 清单。

## 5. 执行记录与协作

需求评审后，开发与测试可以并行。跨边界或高风险变更进行用例评审；开发交付可运行切片时提供提交、构建、环境、真实入口和自测。阶段性交付、跨边界验证、缺陷修复或发布候选使用 `requirements/test-runs/TEMPLATE.md`，记录 AC 结果、数据前后状态、清理、缺陷复测和相邻影响面。普通局部单元测试不创建额外记录。

## 6. 生命周期

- draft：意图仍可能变化。
- ready：AC 已清楚，证据可以规划。
- implemented：代码存在，但证据未全部闭合。
- verified：每条 AC 都有当前、可运行的证据文件。

Issue 可以承载讨论，但合并后的权威故事和 AC ID 应进入仓库，避免 Issue 文本变化后测试失去语义来源。
