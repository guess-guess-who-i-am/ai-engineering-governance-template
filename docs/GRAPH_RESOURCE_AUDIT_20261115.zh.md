# 全局图服务资源审查与修复

本轮降低资源消耗，同时保留全部图节点、两套语言模型、完整文本编码、候选池和评分规则。安装器、直接启动和登录服务统一默认两个计算进程；客户端仍可并发接入，128个在途连接与256个排队位置保持。没有为100个请求创建100份图。

## 根因与修改

1. **调用者上下文误使全局检索缓存失效。** 同一台机器从两个目录发现27个MCP工具，只有 `task_tree_open._meta` 中界面URI的工作区路径不同。旧哈希纳入整个工具对象，切换工作区会反复重建约两万节点、发布并预热四个新进程，旧池期间仍在服务。新哈希只纳入 `graph_from_records` 实际消费的七个字段；完整MCP目录仍保存界面元数据。描述、名称、服务器、身份、输入输出接口及注解变化仍触发更新。进一步实测发现调用者的 `TASK_TREE_QUALITY_MODE` 会将三个工具说明切换成另一套，哈希交替变化；目录发现现隔离调用者的质量模式、执行范围、上下文树和项目根目录四个临时变量，仍允许MCP配置中的显式环境值覆盖。没有删除实际能力说明来掩盖变化。
2. **每份英文向量同时保留装箱浮点和计算矩阵。** 运行时将原向量改为只读连续float32行视图。GraphToolCall原搜索、类别中心和MMR本就转换到float32，因此没有改计算精度、归一化或排序；只删除重复Python对象。真实图加载后单进程物理占用约从2.0GiB降到1.9GiB，收益有限，不将其夸大成主要内存优化。
3. **模型初始化走了GPU再回CPU。** 原生provider自动选设备，而查询最终固定CPU。现在相同模型直接通过官方 `SentenceTransformer(..., device='cpu')` 加载；已有模型转CPU时仍清理无用MPS缓存。没有换模型或量化。
4. **常驻副本过多。** 原四个独立进程各持有完整图、模型及缓存。实测两个计算进程可承接100请求后，将默认副本降为两个。约1.9GiB/份意味着常驻子进程合计约3.8GiB，原四份约8GiB；这是按单进程物理占用外推的近似值，并非精确独占内存总和。真实更新预热时仍可能暂时保留新旧两池；单副本加载峰值仍约3.1–3.4GiB。

监督进程运行33小时，并不表示查询进程持续高CPU33小时。现场新进程每个累计约30–34秒CPU后已空闲；采样栈停在信号量、条件变量等待。降低误重建和副本数可减少加载突发，但真正检索、更新仍需计算。

两进程短查询波次实际存在100个重叠请求；缓存命中与未命中分开报告。长输入均保留原专家2、Skill4、MCP2配额与55秒截止。负载由若干任务家族和不同编号构成，不能代表任意100个互不相关的超长任务。波次顺序运行、系统负载未随机控制，不能宣称固定提速百分比。

锁定同一个真实图SHA，对13类中英文及长任务部署前后逐字段比较，结果及分数完全相等。后续两进程复核曾因合法图更新而SHA不符，该次门禁拒绝，未算成功。数组单测另验证1024×384向量、原始行值及原生top50搜索完全相等。

19项Worker、9项资源图、12项发布、4项CPU设备、2项向量、2项完整窗口编码，以及MCP哈希、真实子进程发现环境隔离、预热和登录服务测试通过；右键部署完整测试通过。治理与25项Skill校验通过。仓库总门禁14/15通过：`document-integrity` 因任务开始前已有的历史版本文件删除失败；未恢复或提交无关删除。大于256KiB的完整Unicode帧修复从已安装版本同步回仓库并纳入回归测试。

完整结果与进程采样在本机 `.reports/graph-resources-20261115/`；脱敏汇总在 [证据JSON](evidence/graph-resources-20261115.json)。未测试硬重启或跨机；已验证LaunchAgent注册、RunAtLoad、KeepAlive及部署器检查。最后以两个真实工作区、advisory/strict两种调用者模式调用全局刷新，耗时0.477秒及0.416秒，图inode/尺寸/修改时间、服务PID及两个查询PID全部不变。最终两个子进程各约1.9GiB物理占用，空闲CPU为0；该物理占用相加不等于排除共享页的精确独占内存。代码升级或真实能力变更仍需必要重建。

## 复测与边界

运行 `scripts/test-graph-resource-identity.mjs`，再运行 `scripts/test-graph-vector-storage.py` 和 `scripts/test-worker-cpu-model.py`。真实服务用 `scripts/verify-graph-resource-results.py` 的 `--output` 保存基线，部署后加 `--baseline` 比较；图SHA变化时必须重新建立基线，不能绕过检查。100请求测试沿用 `scripts/benchmark-graph-load.py --count 100 --long --warm`，分别测试socket、`--pattern stagger` 和 `--transport hook`，避免波次竞争。

更激进的单份图多线程可能受Python GIL影响；共享模型服务或内存映射需要重新设计进程边界，本轮没有未经验证切换。当前仍有约数GiB常驻成本，不能承诺零CPU、零内存或无限并发。来源依据为已安装GraphToolCall 0.46.0的EmbeddingIndex/MMR/预过滤源码、SentenceTransformer设备参数，以及 [NumPy asarray官方文档](https://numpy.org/doc/stable/reference/generated/numpy.asarray.html)。Stack Overflow的mmap/HDF5答案及TEI仓库仅作为候选参考，未作为本次实现或效果依据。
