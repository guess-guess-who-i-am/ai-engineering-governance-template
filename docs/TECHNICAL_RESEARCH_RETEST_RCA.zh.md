# 技术资料自动调用复测：失败边界与修复

2026-10-22。问题是“为什么上次复测失败”，不是重新把组件搜索速度当作完整模型任务速度。

## 1. 已确定的旧失败边界

原自然任务 `01a161a7-3cb1-7673-a048-2290c70b49f6`：technical_research于事件观察起点后约1.0秒报告ready；两个用户Hook共约1.66秒。模型随后在约58.9、141.1、215.2秒报告responseStreamDisconnected，详情分别为Request failed、Request timed out、Request failed；HTTP状态均未暴露。240秒由测试预算中断，网页搜索和资料MCP调用均为0。

所以该次失败不是搜索API执行240秒，也不是MCP始终没启动。第一处可观察异常是模型Responses返回流中断；日志没有提供进一步区分本机网络、中转网关或模型后端的请求ID和服务端错误。不将时间接近60秒当作Nginx超时的证明。

该机器使用自定义Responses提供方，配置为HTTP请求最多4次重试、流重连最多5次。官方Codex实现会在流错误后等待重连；多个采样请求各有重试状态，因此轨迹里可能再次出现“1/5”，不能把分母5理解为整个任务最多等5次。重试会放大坏连接的尾延时，但不是连接最初损坏的根因。

## 2. 本轮对照实验

使用相同默认模型和推理档位、同一提供方、只读临时目录。两个隔离测试仅在线程配置将request_max_retries和stream_max_retries设为0，给90秒总预算；没有改变全局配置，没有降低推理档位、换模型或切换端点。两例同时启动，端到端耗时不作公平性能对照。

- 不需要搜索的控制任务“只回复连接正常”：90.013秒未得到最终回答，MCP已ready，搜索调用为0，也未观测到断流事件。它证明新失败不依赖实际搜索执行；因为只是等待超时，不能把它进一步定性成某个HTTP错误。
- 明确要求调用technical_research_batch：65.399秒完成。首次填timeoutMs=45000，超过工具上限30000，6毫秒即拒绝；模型移除该可选参数后重试，1.514秒从Stack Overflow与GitHub返回6条候选。工具可以被模型真实调用，接口不是必然坏掉；但这不是无需指定工具的自动采用验收。
- 不指定工具名的自然任务：93.254秒完成，无断流，却选普通网页搜索而非资料MCP，故“自动采用”严格检查仍失败。此例UserPromptSubmit为43.868秒，网页工具共8.2秒；它不能套用旧任务“Hook只有1.6秒”的结论。

新自然任务结束后，同一用户问题直接运行路由仅126毫秒，推荐中确有资料MCP。只读健康检查同时报告驻留进程与图/代码代次不一致：索引近期更新会影响冷加载/预热。它是本机慢Hook的具体线索，但尚未记录每个Hook子处理器区间，不能把43.868秒全部归因于图加载。调用正式预热入口时第一次启动触发内部180秒等待超时，未报成功；同一当前图经完整JSON解析有效后，再次启动成功，4个不同进程均加载当前图，内存代码哈希一致。没有把历史日志中的JSON错误直接断定为现存文件损坏，也没有删图、减少Worker数或修改启动超时掩盖问题。

## 3. 已修复的本地问题

测试器原来将最后一条进度说明当作最终回答；旧240秒失败记录里的final其实只是“我会检索”，不是结果。现在只认可final_answer阶段，失败仍保留进度事件但final为空。

测试器原来要求每次都出现候选路由文本，合法零候选会被误判Hook失败。现在分别检查提醒注入和真实Hook生命周期；如果测试目标是资料MCP，单独要求实际调用完成且返回候选，不用“候选名称出现”替代执行。

新增 `codex-retest-diagnostics.mjs`，记录全部可观察重连事件、MCP启动状态、最终回答/进度区别、工具参数错误及是否实际采用资料工具；不从缺失信息推断具体网络跳点。加入可配置但有界的测试预算和模型解析结果、仅安全白名单的测试覆盖项，复现实验不会偷偷更改用户默认策略。

资料MCP现在在工具说明、timeoutMs字段和错误返回中一致声明100–30000毫秒、默认8000；可选参数不需要时省略。非法45000仍拒绝，不静默改成30000，也不把整个工具上限放大到会突破宿主40秒超时。错误返回包含INVALID_ARGUMENT、字段名及合法上下界，让模型只修正该参数。真实MCP客户端正反例核对schema与运行校验一致。不能保证此说明使模型永远不再生成非法参数。

## 4. 哪些问题尚未被本地修改解决

上游Responses流的随机断开和长时间无输出尚未修复；本机没有网关/模型后端访问日志。自动采用也仍未通过：推荐工具可用不等于模型一定选择它；最新普通任务仍使用网页搜索。没有因此在每轮Hook追加长段强制文案，也没移除用户研究方法论来强凑成功。

需要按实际所有者继续处理：

1. 提供方应按本机失败时间及对应请求ID核查：是否在模型仍生成时关闭SSE、是否缓冲正文、是否因代理读超时/模型配额而结束，以及是否正确发送response.completed。请求ID未在当前失败日志中暴露，应从提供方侧关联，不让用户发密钥。
2. 如果代理超时确认为根因，在拥有该代理配置的一侧修读超时、流式刷新与心跳；不能只在Codex增大超时或重试次数。Stack Overflow的Nginx案例只是机制例子，不能证明本机使用Nginx。
3. 对只需要检索的程序工作流，可直接调用已验收MCP，避免为发出HTTP而等主模型生成；这不等于聊天模型的自然任务已经自动采用，也不能把直接工具路径冒称端到端模型提速。
4. 稳定模型通路后，再用不含工具名的同任务多次验收自动采用、来源相关性和输出质量。要改默认重试策略或更换服务商时单独报告取舍，不把少重试称为已修复网络。
