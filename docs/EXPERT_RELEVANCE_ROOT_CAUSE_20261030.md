# 专家为何推荐不相关：逐层实测与修复

结论：问题发生在检索输入、资源描述、候选证据和排序多个边界，不能归因于“模型不喜欢专家”。本轮只上线通过对照的**候选池内向量分数保留修复**；中文任务的真实漏召回和不相关专家仍未全部解决。

## 实测范围与判断边界

复用此前使用频率审计，不重复扫描全部会话。本轮加载本机真实全量图和 GraphToolCall 0.46.0，保持专家 2 / Skill 4 / MCP 2，保留完整专家包和图关系。开发集 42 条中英文查询，其中专家 18 条；新冻结验证集 20 条专家查询。新集在查看边界方案结果前写入，但由调查者编写，未经独立盲标。后续已观察其结果，不能继续称它是新方案的独立保留集。

共保存 1,546 次查询、重排或成对测量记录，重复输入和不同模式均计入，**不是 1,546 个独立任务**。指标为预先列举的目标身份进入席位，不等于全部相关专家的准确率，更不等于实际专家执行成功率。其他等价专家可能被误算为漏命中。

原始报告保留在本机 `.reports/expert-relevance-20261030/`；本文件和实验脚本随私有仓库分发。原始报告包含机器路径，不随 Git 发布。

## 信息流与首次偏差

### 1. 输入丢失任务指代，但简单拼历史不足以解决

`routingQuery` 仅给短句白名单补上下文。真实请求以“为什么不相关？到底在推荐的时候的问题是什么？”开始，共 367 字，虽然历史可读，函数仍原样返回，未带上“专家使用”的前文。

真实全局服务对照：

| 输入 | 推荐的两位专家 |
|---|---|
| 本轮原句 | study-planner、topic-evaluator |
| 前文放前 | ask-liuxiaopai、topic-evaluator |
| 前文放后 | study-planner、topic-evaluator |
| 明确说排查 Codex Skill/MCP 图路由的反事实输入 | txzhaopin、test-results-analyst |

因此，指代信息确实丢失；但“补历史”不是已经验证有效的修复，也不能让用户承担改写任务的责任。本轮未部署猜测性的历史拼接规则。

### 2. 描述索引不等于真实专家适用性

447 位专家的中文编码输入中，427 位超过模型实际的 128 token 上限，76 位的中文完全位于截断之外。英文模型实际上限为 256，不能混为一谈。

`dev-pipeline-orchestrator` 的合成节点 ID 单独占 32 token，中文流程说明完全被截掉。图描述还常包含重复英文与重复示例。原包没有被破坏，但索引表示丢失了能力信息。

还有语义来源不一致：图中 `search-term-analyst` 描述泛化为“搜索意图分析”；原始角色明确是 **paid media / 广告投放搜索词分析**。`agent-orchestrator` 原角色也明确排除通用问答、内容创作和第三方平台配置，图摘要没有完整保留这些边界。这不是单靠提高并发能修复的问题。

实测直接替换为已有的 description-only 向量，专家命中 15/18→14/18；读取原角色正文交叉重排也更差。故没有以“原文更完整”为理由盲目替换生产表示。

### 3. 候选已召回，却被第二次全库截断丢掉向量分数——已修复

原流程先对全量矩阵计算余弦相似度，再取全库前 `max(3×top_k, pool_size)`，最后与候选池求交；只额外补类别前 2/4/2 个向量。

这混淆了**召回后应评分哪些资源**与**最后展示多少资源**。相关专家可能因 BM25 已进入池，却在向量全库排名略低，因而融合时没有该通道证据。缺失分数不代表真实相似度为零。

修复让已计算的矩阵分数覆盖现有候选池里的每个资源，再在最终边界取 2/4/2。没有扩大池、额外编码、增加模型、改变权重或改专家包。非类别请求继续使用库的原有路径。

新验证集的中文 ETL 恢复任务补回 `data-engineer`；分章节研究报告补回 `gpt-researcher-team`。对应回归测试修复前 3/4 失败，修复后 4/4 通过，并覆盖负余弦与线程隔离。

### 4. 相对排名会把弱相关者送入固定席位

当前 wRRF 主要为每通道累计 `effective_weight / (60 + rank)`，并根据前两名分差放大通道权重。它保留相对排名，不能证明候选满足任务条件；弱相关的第一名仍拿得到该通道第一名贡献。后置关键词保护还有固定分差阈值与提升系数，能救回真目标，也会误提升。

例如英文负载实验的向量重排后，APM 与性能测试专家是前两位；后置词法保护把 `growth-hacker` 提上来。直接删除保护又导致专家目标命中 15/18→13/18，所以没有一刀删除。

**固定两席表示类别预算，不是相关性保证。**当前没有经独立标注校准的“此任务适合该专家”判定。新中文事故任务仍推荐财务专家；性能对照任务也会推荐财务专家。这些失败明确保留在报告里，未为追求好数字删除。

## 实验比较与取舍

| 方法 | 开发集专家命中 /18 | 新验证集 /20 | 决定 |
|---|---:|---:|---|
| 当前基线 | 15 | 14 | 对照 |
| 保留池内全部向量分数 | 15 | 16 | 部署 |
| 直接取消后置词法保护 | 13 | 未测 | 开发阶段淘汰 |
| 全池评分 + 类内融合 | 8 | 未测 | 淘汰 |
| 全池评分 + 类内融合及类内词法保护 | 11 | 未测 | 淘汰 |
| 描述向量 + 全池评分 | 14 | 未测 | 淘汰 |
| 专家词法/向量归一化凸组合，向量权重 .25 | 15 | 13 | 不部署 |
| 同上，向量权重 .5 | 15 | 15 | 不部署 |
| 类内词法/向量 RRF | 12 | 未测 | 淘汰 |
| 两通道各前 5 位专家联合 + 多语交叉编码 | 18 | 12 | 过拟合，且增加约 650ms，不部署 |

交叉编码各前 4 位版本新集为 14/20，增加约 539ms，仍不优于已部署的 16/20。原角色正文版本开发集只有 12/18；新集遇到 `industry-service-experts` 入口明确 BLOCKED、没有唯一原角色，因此停止该分支，没有伪造角色或排除阻塞后继续宣称完整成功。随后明确只评估图描述分支。

另测试 MIT 许可的 `intfloat/multilingual-e5-small`：按官方 `query:` / `passage:` 前缀、512 token 和归一化编码447位专家。新验证集纯向量 top2 为 11/20，旧向量同为 11/20；开发专家 7/18 对旧向量 5/18。它不是全图融合对照，不能据此部署。缓存模型的论文结果没有被当成本机效果。

原开发查询中，把图遍历深度降为 0 或取消图候选注入，42 条查询的专家名单均无变化。这说明这批任务不能证明图边为专家推荐提供了增益；不代表图对所有查询无价值。配置里的 graph=.45 是注入参数，不能误说成融合分数的45%。

## 性能、并发与部署证据

20 条查询，每条预热后各跑修复前后 3 次，随机交替顺序，不使用结果缓存：

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| 中位延迟 | 285.13ms | 280.93ms |
| P95 | 599.69ms | 593.71ms |
| 唯一查询目标命中 | 14/20 | 16/20 |

延迟差异很小，未做显著性推断，**不声称明显提速**。这是单进程暖态检索，不是整体任务速度或 token 成本测试。

全局上线仅改运行时 helper，AST 对照证明构图与其他代码不变；图 SHA-256 保持 `9db9afc99e69ae065d59beaae48ae21142872258d0df54979b7c0ea8c7deee6e`。同步现有输入身份记录，避免 Hook 把运行时代码修复误当成需要重建全部向量。

常驻服务在原子替换后自行退出并由既有 LaunchAgent 重启，4 个进程均完成中英预热。62 条真实 socket 请求全部成功，客户端峰值8路重叠、4个查询PID，5.77秒完成，返回名单全匹配冻结实验。该轮内部无重试、无超时；这不等于CPU span证据或100并发验收。另在 `/tmp` 工作区实际执行 Hook，推荐中出现 `data-engineer`。

原始验收第一次失败是 MCP 的实验 ID 与真实 `mcp_original_name` 不同；改用图元数据规范身份后重验。测试失败记录保留，没有把名字转换误差算成生产检索缺陷。

功能检查：候选证据4项、语义保护7项、融合池5项、worker16项均通过；2/4/2 Hook 合约与跟进上下文检查通过。`scripts/check.ps1` 在提交 `ba87660` 上通过全部15个PR门禁，另通过22个Skill验证与任务树精炼门禁。先前失败也保留：密钥扫描把长task文件名中的子串误判为凭据，补边界测试修复；模板自测从Git HEAD导出旧代码，且服务器文档引用了被忽略的本机报告，修正文档并提交后复验通过。没有放宽缺文件检查或跳过安全门禁。

## 查阅的证据与实际用途

- [ToolRet，ACL Findings 2025](https://aclanthology.org/2025.findings-acl.1258/)，DOI `10.18653/v1/2025.findings-acl.1258`：阅读原论文与[代码](https://github.com/mangopy/tool-retrieval-benchmark)。工具检索存在低词面重叠与领域迁移问题，故同时检查全文召回与下游排序；没有宣称复现其43k工具公开榜单，也不冒称ACL主会。
- [ToolRerank，LREC-COLING 2024](https://aclanthology.org/2024.lrec-main.1413/)：阅读原文，以类内多语交叉编码做本机对照；不是完整复现其层级与自适应截断算法。实验负结果见上。
- [An Analysis of Fusion Functions for Hybrid Retrieval，ACM TOIS](https://doi.org/10.1145/3596512)：阅读正文，按归一化凸组合与RRF做对照，权重在开发集比较，新集验证失败后不部署。没有把论文中的优胜结论套到本系统。
- [Scaling Laws For Dense Retrieval，SIGIR 2024](https://doi.org/10.1145/3626772.3657743)：阅读11页原文；提示模型与标注数据规模影响检索，不能把换模型当免验证方案。本轮没有复现大规模训练曲线。
- [Sentence Transformers 检索与重排](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)及[源码](https://github.com/huggingface/sentence-transformers)：GitHub API 当次为19,235 stars；候选召回与重排分开测试。
- [FlagEmbedding 官方重排说明](https://github.com/FlagOpen/FlagEmbedding/tree/master/examples/inference/reranker)：当次12,287 stars；查阅成熟接口，本轮使用已缓存的多语交叉编码器，没有照搬未知权重。
- [Stack Overflow：SentenceTransformer 实际截断](https://stackoverflow.com/questions/71691184/)：读取已接受回答和其官方代码引用，再用本机 tokenizer 实测。另一个领域微调帖子无有效技术答案、BM25帖子无回答，未拿它们当解决依据。[Qdrant混合检索回答](https://stackoverflow.com/questions/79122268/)的 `k=2` 和 rank=0 是特定实现建议，没有替换本库 `k=60`、rank=1。
- [E5 官方模型卡](https://huggingface.co/intfloat/multilingual-e5-small)：确认前缀、池化、长度和许可后实测。免费本地推理，无付费API。

论文的会议/期刊身份按原始出版记录区分；未取得官方年度JCR分区，不把TOIS擅标为某年SCI Q1。资料不相关或无法核验时，不为凑数量扩大引用。

## 仍未完成的目标

本轮可证明候选证据丢失已修复，不能证明“专家已精准自动推荐并执行”。下一步最有价值的是修复索引表示对原角色真实适用范围的丢失，并引入独立相关/不相关标注，分别评估召回、两席精度和拒荐边界；候选分数、模块加载、流程执行和真实产物必须分开计量。未经这组证据，不继续增加经验权重或把新模型直接放入常驻服务。
