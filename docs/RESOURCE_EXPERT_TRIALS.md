# 完整专家模块审计与试用

日期：2026-10-24。范围为本机统一资源库的 447 个专家原包。原包未改写、未拆成多个全局 Skill；本报告中的执行适配在包外完成。不代表已验收所有包，也不代表原 WorkBuddy 宿主功能在 Codex 原生可用。

## 全量静态检查

复现命令：

```sh
node scripts/audit-resource-experts.mjs --source <统一资源库/experts> --out .reports/resource-integration/experts-audit.json
```

实际读取 447 个包的清单、18,553 个文件的哈希与大小，并扫描相关文本的工具/宿主/引用线索。合计 1,558,506,445 字节。447 个 manifest 均存在，声明路径没有缺失。manifest 的 agents 同时存在数组和目录字符串两种格式；目录声明必须展开，不能当作缺失角色。

扫描发现 752 个声明展开入口、agents/ 下 778 个 Markdown 文件（包含辅助文档，不等于 778 个独立角色）、包内 1,448 个 SKILL.md 入口、190 个带脚本的包、58 个有 TeamCreate/SendMessage 显式线索的包。374 条相对路径疑点只是正则候选，并非 374 个已确认缺陷。另有 9 个包要求 `.workbuddy-plugin/plugin.json` 而实际没有该文件，包括架构专家团；它实际使用 `.codebuddy-plugin/plugin.json`。

`gpt-researcher-team` 与 `openspec-doc-team` 检出强制 PASS 条款线索。保持原包不变也不能把该条款产生的 PASS 当作真实验收；适配器必须独立保存通过、失败、未验证状态，不能让角色自述覆盖真实结果。

审计脚本成功扫描退出 0；遗漏必需 --source 参数退出 1；Node 语法检查退出 0。机器扫描不是逐文件人工质量认证，脚本均未自动执行。

## 原包接入契约

图中每个专家包是一个完整 `expert` 节点。清单中的 `agentName` 或 `teamInfo.leadAgent` 指定主入口；命中后仍使用原团队角色、内部 Skill、附件和产物流程。成员不是另拆出去的默认全局入口。

检索文本应包含 name、description、双语 displayDescription、profession、tags、defaultInitPrompt 和 quickPrompts，不能只用人物名或英文角色标题。原始正文与增强检索字段分别存储，检索增强不改写专家方法。

原包按全局来源根保存一次，保持相对路径；只按需读取实际入口及其引用，不把 1.56 GB 全文或全部成员注入请求。单包可能达 641 MB，尤其不能每次路由全文加载。

当前调用契约（2026-10-25）：一次全文读取全局入口即加载原始主角色，原包不拆改，不做宿主工具映射；原工具不可用时报告具体受阻步骤，见[专家统一入口](EXPERT_DIRECT_ENTRY.md)。以下2026-10-24试用曾使用Codex协作工具执行，是历史试验证据，不能当成当前无映射策略下所有团队都可运行的证明；不得用普通文本假装完成 TeamCreate、上传、发布或认证。

## 试用一：开发流水线编排完整模块

原包：`统一资源库/experts/dev-pipeline-orchestrator`。主入口：`agents/dev-pipeline-orchestrator.md`，全文读取，未修改。原模块只有一个编排者定义，其内部要求新上下文执行者、独立问题并行、规格与质量两道评审、真实运行验证。

试验使用独立临时 Git 仓库，固定需求与不可修改的测试，两个互不冲突的任务：有界指数重试、不可变的数值 nearest-rank 分位数。编排者交付 SPEC，两个执行者并行复现失败、各自实现、自审并提交；另一个独立评审者分别给两任务作规格门和质量门，再作全分支终审。主项目与全局配置均未修改。

| 证据 | 实际结果 |
|---|---|
| 基线 `node --test` | 4 项测试，0 通过，退出 1 |
| 执行者独立提交 | retry `3ec1447`；latency `28610e7`；各只改自己文件 |
| 修复后 `node --test` | 4 项通过，0 失败，53.64 ms |
| 独立边界探针 | 60 个断言通过，退出 0 |
| 两任务规格门、质量门与终审 | PASS，未发现可复现缺陷 |
| 范围与卫生 | 原测试未改；主项目未提交；fixture diff 仅两个实现 |

基线提交到最后执行者提交 137 秒；到独立探针落盘为 416 秒（包含模型生成、协调与评审，不是纯函数执行耗时）。token 使用量工具未提供，未知。

可复现材料：`.reports/resource-integration/dev-pipeline-fixture.tar.gz`，不含 Git 元数据，包含 SPEC、原测试、最终实现和 `independent-probes.mjs`。解压到独立目录，执行 `node --test` 及 `node independent-probes.mjs`。临时试验路径为 `/tmp/expert-module-trial.2dtyZk`，不可作为长期依赖。

此结果支持“模块的独立执行、并行与双评审路径可以通过 Codex 的现有协作工具执行”。没有进行同模型无专家对照，不能归因其提高正确率、节省 token 或加速。未测试原宿主、自动模型分级、用户合并/PR选择、长期会话恢复；也未严格验证模块要求的每一步完整代码式计划。试验只覆盖该任务适用的流程路径，不能声称全部指令逐项兼容。

## 试用二：性能测试完整模块

原包：`统一资源库/experts/performance-testing-expert`，主入口 `agents/performance-testing-expert.md`。全文读取，原内容不变，前后 SHA-256 一致。独立试验按基线、场景设计、瓶颈分析、前后验证流程执行。未运行生产负载或付费服务。

固定每次服务约 5 ms，客户端不限制接纳数，仅对照后端信号量容量 1 和 10。每格 5 次测量、先热身，交替两组顺序。错峰输入为第 0/10/20 ms 到达 10/5/20 请求。表中时间是五次运行统计量的平均值，单位 ms：

| 负载 | 容量 1：p50 / p95 / 墙钟 | 容量 10：p50 / p95 / 墙钟 | 每轮成功 |
|---|---|---|---|
| 正常 10 请求 | 26.12 / 53.73 / 53.77 | 5.57 / 5.58 / 5.63 | 10/10 |
| 突发 100 请求 | 275.17 / 520.08 / 549.05 | 27.01 / 52.84 / 54.43 | 100/100 |
| 错峰 35 请求 | 81.39 / 171.03 / 196.86 | 6.01 / 11.13 / 31.00 | 35/35 |
| 同一后端重复两次 100 请求 | 280.42 / 528.23 / 1110.19 | 29.30 / 54.65 / 113.01 | 200/200 |

40 次测量共返回 3,450 个正确且唯一的结果 ID，零重试；实测服务并发峰值分别为 1 和 10，并由逐请求服务时间区间独立重建确认。每轮队列、活跃服务和客户端在途数归零。100 请求突发时，两组客户端接纳峰值都是 100，因此瓶颈确实位于后端容量，不是客户端有没有同时发起。

完整脚本、逐请求数据和带 95% Student t 区间的报告已保存为 `.reports/resource-integration/performance-fixture.tar.gz`；解压后在目录中执行 `node trial.mjs` 可重跑。临时路径 `/tmp/performance-module-trial.2OQTXf`。Node v24.21.0 / darwin arm64；token 使用量未知。置信区间只描述五次本机合成运行间变异，不证明生产 SLA。

结果说明这个完整模块的性能工作流可以执行并形成可检查产物。吞吐差异来自人为改变后端容量，不能归因于专家模块，也不能声称生产已有加速。具体信号量观测和 ID 完整性探针来自试验约束与实施判断，原模块未提供直接可运行实现。未测试耐久、真实失效极限、Core Web Vitals、CI/生产监控或业务 ROI；其 FID 表述与“core training”说明也不能单独作为现行标准或技术依据。未做专家对无专家对照，不判断其宣称的 25% 改善、10 倍扩展或 90% 事故预防目标。

## 全局安装后的独立内容核验

`scripts/verify-resource-packages.mjs` 对实际全局 catalog 只读，输出 `.reports/resource-integration/package-integrity.json`。核验时 catalog 有 4,232 个模块：447 专家、3,307 个 Skill 包版本、478 个 MCP 服务描述符。

检查专家源目录和已安装包内每个原文件的 SHA-256 是否仍等于本轮源审计；Skill 入口必须使用实际 `module.path` 对照 `entry_hash`，同时检查原始 Skill 入口，避免嵌套 Skill 错查父专家根的 SKILL.md。MCP 仅检查自有描述符存在且非空，未打开源 credential 文件、未声称认证或功能可用。

实际安排 44,187 个检查、42,617 个唯一哈希文件路径，20 并发，实测同时文件读取峰值 20。最终运行 5.28 秒、0 个差异。catalog 未修改。

安装清单有 45 项明确排除（专家 11、Skill 34），都记录了原因。结果为 `MATCH_WITH_EXPLICIT_OMISSIONS`，`completeOriginalPackagePreservation=false`；这表示已核验文件匹配，并非原包所有文件完整无损。完整排除项与原因以报告为准。独立核验只覆盖上述范围，不是包内脚本或全量功能验收。

## 自动推荐专家的针对性路由实验

日期：2026-10-25。使用 `scripts/resource-expert-routing-challenge.json` 中不含模块名称的中英文请求，真实全局 Hook 输出 top-4；另对同一全局 GraphToolCall worker/socket 扩展候选深度，分开观察图召回与 Hook 截断。结果文件为 `.reports/resource-integration/expert-routing-challenge-global.json` 和 `.reports/resource-integration/expert-routing-ablation.json`，后者保留四种隔离条件的逐请求结果。没有改动生产 Hook、图、worker 或全局配置。

Hook 消融共 14 个请求/条件（4 类专家任务各中英一条，另有 MCP、Skill 控制项）。baseline、去掉本地词面补位、去掉 alias 提升、两者都去掉，目标名称都为 4/14；专家目标命中都为 2/8。去掉本地词面补位没有改变本挑战集目标命中数，因此它不是本轮漏召回的主因。alias 提升会影响部分方法 Skill 的候选排序，但在小样本中没有提高目标命中总数。

| 无名称任务 | Hook top-4 专家命中 | 图候选中的目标位置（中文 / 英文） | 诊断 |
|---|---:|---:|---|
| 并行研究、独立核验、汇总报告 | 0/2 | `gpt-researcher-team` 第 8 / 5；英文另有 `deep-researcher` 第 32 | 中文目标刚落在图 top-8 之外；英文也会被 Hook top-4 截掉 |
| 跨专业架构角色交接 | 1/2 | 架构专家团第 33 / 1 | 中英文排序差异大；中文超出 Hook 候选深度，英文进入 top-4 |
| 并行开发、规格门与质量门 | 0/2 | `dev-pipeline-orchestrator` 第 49 / 39 | 两种语言都被 Hook top-4 截掉，图排序也靠后 |
| 性能实验、瓶颈分析、前后验证 | 1/2 | 中文前 50 未出现目标；英文 `apm-performance-expert` 第 7、`performance-testing-expert` 第 22 | 中文不是增大 Hook top-k 就能解决；英文完整性能测试专家也被 top-4 截掉 |

候选深度查询参数请求 100 项，但该 worker 实际只返回 50 项；名次均按实际返回列表计算。同一中文架构请求在先前 top-32 查询中排第 21，在 top-50 查询中排第 33，名次并非随 K 扩大保持不变，说明图检索的候选深度可能影响排序/候选集，不能把结果简单解释为固定排序被 top-4 截断。Hook 原始挑战中专家任务精确入口只在架构英文与性能英文两条可见（2/8）；MCP 对照 Context7 中英均命中。Skill 两个对照均未命中预设目标集合，说明问题不限于专家，也可能是本挑战目标集合与可接受替代模块定义不足。名称可见率不能替代工作流等价审查。

**根因判断**：现象不是“Hook 每次只等 12 秒”造成的。主要有两层：其一，固定 top-8 图候选与 top-4 Hook 注入预算截断了部分靠后的模块；其二，更上游的图召回/排序对中文弱且跨语言不稳定，开发流水线模块甚至排在 39/49。只加 Hook 等待时间或放大注入数不能找回图服务没有给出的结果；盲目把候选数扩大到 50 也只会增加低相关候选竞争和上下文成本。

下一步应先扩充多语、无名称、带能力判据的冻结留出集，并标注“完整模块与等价替代”及其必需动作/产物；再离线比较双语描述增强、召回融合与能力/工作流重排，分别报告专家/MCP/Skill 的 Recall@K、MRR、误推荐率、Hook 注入 token 和延迟。通过留出集后才考虑部署候选融合。当前实验未测试 token 消耗、路由准确率的总体估计或生产任务成功率；小样本结果用于定位，不是普遍性能结论。
