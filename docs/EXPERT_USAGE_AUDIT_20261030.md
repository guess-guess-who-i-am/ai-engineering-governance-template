# 专家真实使用频率审计

结论：当前证据支持“专家没有形成稳定的自然使用”。推荐在发生，完整读取很少，而且已确认的读取全部集中在专家审计或用户要求的试用中。不能再用“447 个专家已注册”“Hook 有两个专家席位”证明专家被实际使用。

本轮只审计，没有改推荐、专家包、Hook 或服务。复用本机日志与已有试验，不以论文或新自测替代真实使用记录。

## 范围与统计

窗口为 UTC 2026-10-24 00:00 至 2026-10-30 00:00（不含终点），排除本次审计。扫描本机 active/archive 的 77 个 JSONL，按实际 thread/turn/item ID 去重，取得 18 个线程中的 191 个人类消息触发轮。统计覆盖有持久记录的本机 Codex 会话，不代表所有电脑或所有入口。

10 月 26 日以后单独统计：75 轮中 65 轮有专家候选，但只有 2 轮确认完整原文加载，仍属于审计/试用。低采用不能仅由早期未安装解释。

候选涉及 73 个不同专家；最高频的 `xiaot`、`metamorphosis-practitioner` 各出现 7 轮。现有样本没有显示“永远只有两三个专家被推荐”，主要问题是相关性和采用之间的断裂。

完整读取涉及 `dev-pipeline-orchestrator`、`apm-performance-expert`、`code-review-expert`、`performance-testing-expert`、`skill-smith`。8 条全文读取证据属于 4 轮，包含同一角色重复读取，不能报成 8 次专家任务执行。

## 首次流失与根因

1. **类别排名不等于任务适用。** `prepare_category_slot_retrieval` 按最终分数取各类别前列；专家 2 席保证类别覆盖，没有在这一步验证输入、输出和流程适用性。实际 IDE 接入任务收到 SEO/PPT 专家，随后读取了股票分析专家作为接入检查；另一个路由优化试用收到腾讯地图问数与 Skill 包制作专家。不能据这些例子推断整体错配率，但它们证明错配确实发生。
2. **推荐到执行的边界没有闭环。** `renderRoutingContext` 输出候选和读取路径，并要求只选择直接适合任务的入口；GraphToolCall 不执行原专家流程。模型忽略无关候选是合理行为；“Hook 已输出两个专家”不是有效使用证据。宣传文案任务也曾收到相对对口的 `proposal-strategist`，却未发现完整读取，说明不能把所有流失都归咎于无关推荐；这一案例未采用的模型内部原因无法从日志证明。
3. **原包不总能在当前宿主执行。** 既有试用明确记录 `skill-tester` 依赖宿主没有的 `Skill` 工具；其他团队的原生编排工具也未逐项证明可执行。保留完整原包后，读取入口成功仍不解决这些依赖。此前临时真实 turn 虽加载了性能专家，却被中止；合成审查和后端试验有产物，但不计作自然使用。
4. **历史可观测性不足，旧统计还会误判。** 旧审计只看终端，不能覆盖 IDE；初版把 `cat` 当作完整读取条件，会漏掉用 `sed` 读完的短文件。反过来，带原角色头标记的输出也可能在持久化时被截断。最终统计以完整原文在成功命令输出中出现为依据。未匹配全文只是未确认，尤其日志截断不能证明模型当时没收到全文。

此前 SSH 核验的 110/194 缺专家注册表和完整专家包，可解释远端缺入口；这是前次部署快照，本轮未重新测远端，也没有把本机频率外推到服务器。

## IDE 的独立证据边界

发现 2,294 份持久对话与 319 份执行诊断，共 25,410 条结构事件。对话存储明确只保留 user/assistant 文本，不保留完整工具调用结果。诊断中 310 条 `skills_read` 完成记录按运行 ID、调用 ID、事件去重后为 **309 次**；这些历史事件均没有资源 ID、类别或路径，无法区分普通 Skill 与专家。

因此不能说“IDE 从没用过专家”，也不能拿这 309 次读取证明用了专家。当前源码已有专家入口身份的诊断分支，但历史日志不能补回当时未保存的信息。需要以后用真实任务留下“资源身份→成功加载→原流程产物→验收结果”的宿主回执，才能可靠测执行率；本轮没有擅自修改此机制。
