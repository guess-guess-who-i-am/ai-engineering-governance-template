# 专家推荐评价指标审计

**用户的质疑成立：49/68（此前类似的48/68）不能解释为推荐正确率。** 本次发现评价指标失真，也复现了评价输入与真实追问不一致的问题。生产排序、专家原包和全局服务未修改；真正的整体适用率、可执行率、任务成功率目前未知。

## 1. 计分实际测了什么

`scripts/experiment-expert-relevance.py` 中，`rank` 是返回结果里第一个预设目标 ID 的位置，`hits` 只数 `rank is not None`。当前专家配额为两席，预设目标任意一个进入结果即记一次命中。没有检查两位专家的原角色是否适合当前任务，也没有检查运行条件或交付产物。

独立从已提交的冻结结果重新计算，逐条验证名称成员关系与存储成绩一致：

| 测量 | 结果 | 能说明什么 |
|---|---:|---|
| 场景 / 中英查询实例 | 34 / 68 | 不是68个独立任务 |
| 至少一个预设目标命中 | 49/68 | 仅为目标名称命中 |
| 两席中含0 / 1 / 2个预设目标 | 19 / 44 / 5条 | 不是不相关 / 部分相关 / 全相关标签 |
| 中文 / 英文目标命中 | 23/34、26/34 | 同一场景的语言版本，不能当独立抽样 |

**反事实负控：** 对每条结果保留一个已命中的目标，把另一席换成刻意不相容的测试占位专家，旧分数仍49/68；把全部专家标成执行阻断，旧分数也仍49/68。68条逐行分数均不变。这证明指标不感知这两种退化；测试中的替换与阻断是合成干预，不是真实检索结果或线上故障。

复现：

```sh
python3 scripts/audit-expert-recommendation-metrics.py --report docs/evidence/expert-metric-audit-20261030.json
node scripts/audit-expert-routing-context.mjs docs/evidence/expert-metric-context-audit-20261030.json
```

计分输入来自4份题集，均记录文件哈希。首次审计漏传其中2份时直接失败，没有跳过缺失标签。空数据、存储成绩与重算不符也会拒绝。

## 2. “命中”中的真反例与“未命中”中的标签缺口

以下为定向诊断，不是随机抽样，也不是独立盲评；不能外推总体错配比例。判断依据为完整原主角色中的职责、服务范围和约束，证据文件记录原文件哈希与原文行号。

| 请求与真实两席 | 旧分数 | 原角色审查 |
|---|---:|---|
| 线上支付大面积故障：`incident-response-commander`＋`studio-producer` | 命中 | 第一位负责事故恢复；第二位负责创意工作室战略、创意愿景与项目组合，领域错配被漏罚 |
| 储能争议证据报告：`gpt-researcher-team`＋`valuation-reviewer` | 命中 | 第一位研究流程相关；第二位处理基金季度估值和LP报告，领域错配被漏罚 |
| 中文核心和SCI选刊：`academic-journal-selector`＋`arxiv-watcher` | 命中 | 第二位的原职责是ArXiv检索、摘要和速报，不覆盖此处选刊产物 |
| 三个月考研复习计划：`exam-preparation-planner`＋`ket-prep-team` | 未命中 | 标签只有`study-planner`；第一位明确允许长期高竞争考试的通用规划，具有规划价值但不能冒称专项权威；第二位面向少儿KET/A2，错配 |

这同时证明两件事：命中不能保证另一席适用；未命中不能证明两席都无用。**不能把所有非目标专家都记为0分，也不能把有通用规划价值提升为完整满足全部硬约束。**

运行条件需要单独核验。例如研究团队原角色要求`TeamCreate`和特定`Agent name/subagent_type`，当前会话没有这些原接口，不能仅凭相关名称声称按原流程已执行。相反，“设计供应商付款流程”并不要求当场真实付款，不能因没接支付API就判语义推荐错误。

## 3. 真实追问为什么不在旧测试的覆盖内

用真实`routingQuery`入口、合成的一条前置任务记录，复现用户本轮追问：

| 输入 | 是否保留上文Skill/MCP路由主题 |
|---|---|
| “继续”，2字 | 是 |
| 用户本轮原话，95字 | 否，原样作为查询返回 |
| 原话追加检查要求，123字 | 否，原样返回 |
| 独立新话题“预订东京酒店” | 否，符合预期 |

所属边界是`skill-router.mjs`的查询构造：`isFollowup`只识别有限的短跟随表达；超过100字直接拒绝继承。**95字例子已说明问题不只是100字上限，有限词表同样会漏判有内容的追问。** 于是“评价指标、推荐”带着缺失的指代对象进入检索，可能被误解为内容评价、职业推荐等任务。

这次仅证明输入主题未恢复；没有再次运行图检索，不能声称这四例给出了端到端误推荐率。旧题集大多独立写明任务对象，不能代替真实长对话追问测试。

## 4. 根因链与应采用的评价边界

根因不是单纯“公式不够复杂”，而是把**预设名字成员关系**作为了**用户任务适配性**的代理。再加上标签不完整、两席错误不扣分、开发题与长追问分布不同、推荐与执行没有分开，改进代理分数就可能不改变用户体验。题集已用于多轮方案比较，后续不能继续称盲保留集；题目、标签与方案评价缺少独立验证，存在循环确认风险。

后续评测应分别回答以下问题，保留各自分母，不拼成未经校准的单个总分：

1. **请求理解：** 从当前对话冻结任务对象、动作、必需产物、硬约束；带有指代的真实追问必须用对应历史。加入新话题切换，避免盲目拼接旧需求。
2. **逐席适用：** 按原角色判直接适用、局部辅助、不适用或证据不足；附原文依据。分别统计至少一位能承担主要任务、无关席位、关键约束覆盖。局部辅助不等于无关，两个同类专家也不保证互补覆盖。
3. **当前可执行：** 只核对当前任务确实需要的原工具、内部材料、授权及宿主前置条件；设计任务与实际操作任务分开。
4. **真正使用与产物：** 记录是否加载原角色、是否按原流程执行、实际产物是否通过预先冻结的任务验收；加载成功和工具返回正常均不能当作任务成功。
5. **端到端收益：** 在同任务、同模型和资源条件下比较实际任务通过、总token和墙钟时间。语义相似度、socket成功率、单次检索延迟不能替代这些结果。

标签以返回结果和不同方案候选的合并集合补齐，隐藏排名、方案来源和旧目标名；保留未知，不把未标注候选当无关。按会话/场景分组保留测试，中文与英文成对分析；加入领域相似但硬约束不符、没有合适专家、缺信息等负例。固定2专家席位目前保持用户设置，但评价必须揭示不必要推荐，不能因配额而免罚。

用LLM判断语义时，应先校准正确、领域错配、局部辅助、运行阻断等样例，检查交换展示顺序后是否一致，并用任务产物作交叉验证。本轮主模型的原角色审查仅是初步诊断，不能宣称已经完成独立盲评。尚无足够证据设定“合格准确率”数值，不任意给阈值。

## 5. 外部依据与证据限制

- [ToolSandbox官方实现](https://github.com/apple/ToolSandbox)：已读取README的Evaluation部分，按关键里程碑、轨迹状态与依赖顺序评价结果，明确不同工具路径可以完成同一任务，并测试信息不足；支持将“指定名称命中”与“任务达成”分开。论文为[NAACL 2025 Findings](https://aclanthology.org/2025.findings-naacl.65/)，DOI `10.18653/v1/2025.findings-naacl.65`，不把Findings称作CCF-A主会。本轮借鉴评价设计，没有运行其完整benchmark。
- [Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena](https://arxiv.org/html/2306.05685)：已核对§3的顺序偏差、冗长偏差、参考答案辅助与交换顺序方法。论文对自偏好的讨论本身保留不确定性；不能借其结果证明本系统存在相同偏差，也不能把论文的人类一致率搬作本评审器的准确率。
- Stanford IR页面两次TLS失败；另一排名评价文档地址返回404，均未用作已阅读证据。没有运行付费模型或调用真实付款等外部操作。
