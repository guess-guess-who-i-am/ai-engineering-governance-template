# 完整专家工作流实测与根因报告

日期：2026-10-25。范围是本机当前全局路由、完整专家入口和三个隔离工作区实验；没有修改生产 Hook、图、注册表、专家原包，没有部署远端，也没有把合成实验当成真实模型质量评测。

## 结论

完整专家本身可以按原流程产出可验证结果，但“自然任务自动推荐”仍不可靠：三个任务中只有性能任务自然命中目标完整专家；审查任务自然漏召回，后端任务召回了错误的媒体归档专家。点名并不总能修复：审查的中文长任务仍漏，短中文名称、英文长任务才命中。

| 工作流 | 路由 | 实际产物与验证 |
|---|---|---|
| `performance-testing-expert` | 自然任务首位命中 | 30 组交替测量，1050 个结果 ID 全正确；容量 1/6 的正常、突发、错峰平均 p95 均显著降低。瓶颈是合成队列容量，不归因于提示词。 |
| `code-review-expert` | 自然和中文长点名均未进入 Hook 前 8；仅名称/短中文/英文长请求命中 | 未修改白盒 fixture；3 项契约测试均失败，复现路径穿越、并发丢更新、空数组返回 NaN，探针确认 3 条反例。 |
| `backend-architect` | 自然任务首位是 `mibao-media-archivist`；带名称控制命中 | 单进程不可变索引模型 6/6 测试通过；10/5/20/65 错峰 100 请求期间切版，旧请求全读版本1、新请求读版本2，混版负对照可被识别。不是实际 HTTP/IPC 服务。 |

## 检索断点

对常驻 worker 做了函数级只读追踪，返回候选与生产 Hook 一致。

1. 审查自然任务的目标专家在 BM25 词法排序约第 808 位，embedding 全库约第 1778 位，未进入 500 项预过滤池。之后即使名称优先和 Hook 的 top-4 展示逻辑运行，也没有候选可提升。这是首次不可逆的漏召回边界。
2. 后端自然任务的目标专家词法约第 9 位、进入预过滤池，但融合后降至第 72 位；`mibao-media-archivist` 的 embedding 约第 12 位并最终排第 1。媒体专家描述重复“本地索引、更新、原件不动”等泛化词，和任务表面词重合，形成错误首选。这是弱排序和类型错配，不是召回失败。
3. 中文长点名的目标专家在词法约第 54 位、embedding 约第 477/99 位（全库/池内），最终仍没有前 8；同一名称的短中文请求可进第 1，英文长请求也可进第 1。故不能把问题归结为“中文模型完全不可用”；查询长度、中文通道的分词/向量与候选池共同影响结果。
4. 当前节点的 `api_contract.produces/consumes/links` 对实测资源为空，图没有可用于“任务动作→产物→专家”的强约束。图候选因此更多依赖描述相似度，而不是可验证的工作流产物关系。
5. Hook 明确点名只会在 `scored + graphScored` 已返回的项目中置顶；它不是全图名称索引。把 Hook 等待时间或最终候选数调大，不能修复上游池外漏召回。

## 完整专家的执行边界

性能专家入口原文完整读取，原文仍有 FID 等过时网页指标、25% 改善和 90% 事故预防等模板化目标；本实验没有把它们当证据。后端专家额外触发了包内 `fullstack-dev` 约 34,946 字节和测试参考约 11,818 字节，其中很多前端、数据库和认证内容与本地索引模型无关，说明完整专家可用但上下文成本偏宽。原专家是方法型提示词，不是已经注册到宿主的可执行程序；入口成功不等于原生工具、宿主绑定或业务完成。

## 证据文件

原始任务、路由结果、阶段追踪、失败输出和业务产物均保留在 `.reports/expert-workflows-20261025/`：

- `routing.json`、`routing-diagnosis.json`、`stage-trace.json`：路由与阶段证据；`*-initial.json` 保留首次诊断/脚本失败记录。
- `performance/measurements.json`、`performance/REPORT.md`：性能专家测量。
- `review/spec.test.mjs`、`review/counterexamples.json`、`review/REVIEW.md`：审查反例。
- `backend/model.test.mjs`、`backend/concurrency.json`、`backend/REPORT.md`：后端一致性验证。
- `execution-receipts.json`：三组命令的真实退出码和 stdout；审查测试退出码 1 是预期发现缺陷，不是测试基础设施失败。
- `boundary-verification.json`：生产四个关键哈希前后不变，三份专家入口与当前原始主角色字节一致；同时记录了全局 `hook-dispatch.mjs` 与仓库副本存在一个 Windows 默认路径差异，本轮未改动。

## 限制

这是三个有针对性的诊断任务，不是代表性召回 benchmark；没有独立 LLM 无专家对照、长期线上准确率、真实多进程部署、生产 SLA 或 token ROI。性能数据只证明合成容量变化的排队效应。后端模型的“100 并发”是单进程合成屏障，且满载第 101 请求按契约拒绝，不能宣称生产中 100 个请求都成功。

本轮结论是定位问题，不是修复完成：当前最应修改的是候选池的召回边界、完整专家/辅助 Skill 的类型与产物关系，以及泛化描述造成的二阶段排序；不应只调 Hook 的等待时间或最终展示数量。
