# 项目生命周期与交付门禁

这套生命周期约束完成声明，不要求每个小改都产生一套重文档。

## 工作对象

- `User Journey`：一个结果跨多个 Story、模块、服务或阶段时使用；单一闭环可以省略。
- `User Story`：一个可独立验收的用户或系统结果，带稳定 `US-nnn` 和 `AC-nnn`。
- `Build Plan`：仅用于高影响歧义、跨边界实现、数据迁移、复杂发布或回滚；可逆局部修改不强制创建。
- `Task`：实现步骤，放在 Plan、Issue 或当前执行系统中，不建立与 Story 竞争的第二套需求层级。

顺序通常是：`Journey（按需） -> Story -> Plan（按需） -> 实现 -> 证据 -> PR -> 集成 -> 发布`。

## Gate 0：项目可开工

- 用户、结果、第一条真实闭环和非目标明确。
- 核心术语、所有权和跨系统边界已记录。
- 必需测试类别已在 `quality/gates.json` 中明确为 `active`、`planned` 或 `not-applicable`。
- 项目需要的持久、稀缺、付费或承载数据资源已有负责人和退出方式。
- GitHub、分支保护、秘密边界和真实工程命令已确定，或以会阻止发布的 `planned` 项明确保留。

Gate 0 不要求把未知数字填满。没有证据的并发、容量、成本或截止时间不得虚构。

## Gate 1：Story 可实现

- Story 有 Actor、Need、Value、范围和至少一条主路径验收条件。
- 高风险 Story 有相关失败、权限、边界或恢复条件。
- 父 Journey、依赖、公共 contract 和资源影响已确认；不适用时明确写无。
- 只有真正影响实现方向的歧义仍未关闭时才建立 Build Plan。

## Gate 2：Story 可审查

- 真实入口、输入、输出和消费者路径已经运行。
- 每条验收条件映射到当前提交上的可复现证据。
- 相关 contract、迁移、资源、运行说明和完整 diff 已同步审查。
- P0/P1 Finding 已关闭；未验证表面、P2/P3 风险和回滚边界已明确。

## Gate 3：可集成

- 在受保护合并候选或干净工作区验证，不依赖未提交文件、个人缓存或本机秘密。
- 跨组件 contract、Flow、迁移顺序和共享资源没有漂移或冲突。
- 多个 Story 按真实依赖集成；绿色分支不自动等于所有内容都应发布。

## Gate 4：可发布

- 冻结精确提交、Story/PR 清单和制品摘要。
- 只部署已经验证的同一制品，并完成目标环境 smoke 与观察。
- 配置、监控、告警、迁移、恢复和回滚触发条件可执行。
- 发布证据对应当前环境与提交；不能用旧结果或文件存在代替。

## 交付模式

单模块、一个协调发布流且 `main` 始终可发布时，可以直接通过受保护 PR 合入 `main`。跨模块、并行集成、选择性发布或独立集成环境需要更明确的集成候选。模式可以简化分支，但不能删除 Story、证据、审查、制品身份和回滚要求。

Hotfix 必须从已部署标签或精确提交建立，验证“生产基线 + 最小修复”的制品，再回流主线；不能把包含未部署内容的新 `main` 当作生产基线。

## 优先级

- `P0`：安全、数据或主流程阻断，立即处理。
- `P1`：当前发布或核心路径必须完成。
- `P2`：正常产品与维护工作。
- `P3`：不影响当前交付的改进。

优先级只决定顺序，不降低验收、所有权和证据要求。
