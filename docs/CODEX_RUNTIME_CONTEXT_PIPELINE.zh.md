#### `task_tree_*` 为什么会出现在 schema 中，以及能否修改【对应运行时：task_tree MCP 初始化/`tools/list` 时读取；重启或新会话可能再次读取】

当前 `config.toml` 明确把 `task_tree` MCP 指向：

```text
D:\Nodejs\node.exe E:\解决跟不上大模型思路问题\llm-task-tree-kit\scripts\mcp-server.mjs
```

该服务器在 `scripts/mcp-server.mjs` 中定义每个工具的 `name`、`description`、`inputSchema` 和 handler，并在 MCP `initialize` 响应中声明一段服务器级 `instructions`。因此模型会在工具定义阶段看到这些内容：

- 可以改 `description`：修改模型看到的工具说明。
- 可以改 `inputSchema`：修改参数名称、类型、必填项和枚举；但必须同步 handler，否则工具会变得不可用。
- 可以改 `instructions`：修改服务器级使用提示。
- 可以改 handler、服务端 API、精炼门禁和权限检查：这才会改变真实行为。

仅修改描述不会改变行为；仅修改源文件也不会立即影响已运行的 MCP 进程。需要重启 MCP 或新建会话，让 Codex 重新执行 `initialize`/`tools/list`。如果实际使用的是插件缓存副本，还必须修改并重新安装/刷新对应插件，否则改的不是消费者正在运行的副本。

当前 `task_tree_write` 的“自动备份、精炼门禁、保护 GraphState、返回实际 changes”等内容，既写在工具 description 中，也由服务端 handler 实际执行；只能改文字而不改 handler，会造成模型认知与真实行为不一致。

### 5.4 实现流程（项目英文源完整中文翻译）【对应运行时：项目入口加载一次；工程任务执行时按阶段使用】

1. Discover（发现）：确认当前状态、真实消费者和第一个信息流边界。
2. Freeze（冻结）：只针对高影响的歧义创建简短的 build brief。
3. Minimal closed loop（最小闭环）：先完成一条可运行的端到端路径。
4. Extend（扩展）：在这条路径之上增加状态、边界和质量属性。
5. Verify（验证）：从最窄的证据开始；跨越边界时增加 contract 或 E2E 证据。
6. Deliver（交付）：说明结果、证据、限制以及下一个尚未完成的事项。

### 8.7 Hook 合并【对应运行时：每个 Hook 事件一次；等待并行子处理器后合并为一次 additionalContext】

三个子处理器通过 `Promise.all` 并行。dispatcher：

1. 等待三个处理器全部完成或各自超时。
2. 保留非空 `additionalContext`。
3. 根据 Skill 路径去除重复候选。
4. 合并为一次 Hook 输出。

Skill Router 的 Node 主路径和 PowerShell 回退路径都遵守同一闸门：项目级、用户级、Codex、任务树和外部 Skill 先统一索引/评分/去重，最多输出 4 个带来源的精确路径；回退路径也不再注入完整 description。
5. 子处理器错误写到 stderr，其他成功结果仍继续返回。

当前超时：context 7 秒、Skill 12 秒、Capability 12 秒、外层 Hook 20 秒；每条消息 additionalContext 上限 14,000 字符。

## 9. 模型请求和上游 Router【对应运行时：每次模型 API 请求经过一次；重试/故障切换时同一逻辑请求可能多次触达上游】

3. 在健康路线中按活动请求量选择。
4. 发生网络错误、可重试状态或流启动失败时执行重试/故障切换。
5. 将上游流式响应转回 Codex Desktop。

Router 不负责选择 Skill、任务步骤或验证标准；它只负责模型 API 请求的转发和可靠性。

## 10. 模型收到上下文后的分叉【本文档流程说明：仅在阅读本文档时读取；实际分叉由模型每轮决策】

### 10.1 直接回答【对应运行时：满足条件的某一轮执行一次；不读取额外 Skill/工具】

如果任务只是解释且不需要外部证据或文件检查，模型可以直接给最终回答。

### 10.2 读取 Skill【对应运行时：每个被触发 Skill 在首次使用时完整读取一次；同一轮可能读取多个，后续是否重读取决于模型/压缩】

如果用户点名或 description 明确匹配：

```text
先告诉用户为什么使用该 Skill
→ 完整读取 SKILL.md
→ 只读取 Skill 指向的必要参考
→ 按 Skill 工作流执行
```

Skill 路由器没有推荐，不等于模型不能触发 Skill；模型还会根据平台提供的 Skill description 自行判断。

### 10.3 调用 Capability【对应运行时：出现强候选的轮次调用；每次 `capability_execute` 一次，后续契约可能继续调用记录工具】

强候选出现后，模型调用 `capability_execute`：

- `verified-adapter`：适配器已经执行，模型检查回执并交付。
- `requires-agent-actions`：模型继续调用普通工具完成步骤，验证产物，再调用记录工具。
- 不可用或弱匹配：模型从项目现状重新实现。

### 10.4 普通工具循环【对应运行时：每个工具波次重复执行；UserPromptSubmit Hook 不在波次之间重新运行】

模型可以：

```text
形成当前可确定的操作集合
→ 并发执行独立工具
→ 工具结果加入对话上下文
→ 模型解释新证据
→ 决定下一波工具/询问用户/停止
```

`UserPromptSubmit` Hook 只在用户消息到达时运行一次，不会在每次工具调用前重新运行。后续工具波次是否继续并发，依赖模型记住本轮并发契约。

### 10.5 用户中途发新消息【对应运行时：每条排队的后续消息重新进入 UserPromptSubmit；新目标覆盖旧计划】

本地设置为 `followUpQueueMode = "queue"`。新消息进入队列；处理时，平台和全局 AGENTS 都要求把用户最新要求视为当前目标，旧计划冲突时停止旧计划。

## 11. 完成和最终回答【对应运行时：每个任务结束阶段执行；当前没有统一 Stop Hook 自动读取或拦截】

当前没有配置统一的 `Stop`/“完成前验证” Hook。完成流程主要是：

1. 模型根据项目 AGENTS 和已加载 Skill 选择验证。
2. 修改跨边界或完成证据不明确时，应触发 `verify-before-completion`。
3. 工具或测试产生真实结果。
4. 模型判断验收是否满足。
5. 最终回答说明结果、证据、限制和未完成项。
6. `notify = turn-ended` 只通知本轮结束，不验证任务完成。

因此，“必须验证后才能完成”目前主要是模型规则；只有具体测试、schema、task-tree 写入门禁和 CI 在被实际调用时才是机械强制。
