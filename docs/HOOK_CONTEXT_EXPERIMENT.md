# Hook 注入频率实验（2026-10-10）

## 问题与测量边界

用户希望判断固定提醒能否每 3–4 轮注入一次，从而减少上下文占用和等待时间。用当前已安装的 macOS 全局 Hook，以同一工作区依次提交四个不同提示，分别调用 `context-refresh.mjs`、`skill-router.mjs` 和正式入口 `hook-dispatch.mjs`。记录 `additionalContext` 的 UTF-8 字节数、进程耗时和 Skill 候选；不输出提示之外的配置内容。

这里的“字节数”是 Hook 发给 Codex 的文本量，**不是模型输入 token、计费量、缓存命中量或上下文窗口占用量**。后面两种频率是基于实测输出的重放计算，没有改动生产 Hook。

## 实测

| 提示 | 固定提醒与方法路由 | 动态 Skill 路由 | 完整 Hook 输出 |
|---|---:|---:|---:|
| `hello` | 8,756 B | 2,465 B | 11,223 B |
| 合并冲突根因分析 | 8,756 B | 1,415 B | 10,173 B |
| 更新 README 安装说明 | 8,756 B | 1,598 B | 10,356 B |
| 安装一个新 Skill | 8,756 B | 2,362 B | 11,120 B |

四轮完整输出共 **42,872 B**；固定部分共 **35,024 B**。固定部分单次约 36–44 ms；首次独立 Skill 路由调用约 8.2 s，后续样本约 1.1–3.4 s。完整 Hook 的后续样本约 0.9–3.5 s。两个子 Hook 在 dispatcher 内并行，故删除固定部分未必能显著缩短等待；主要等待来自动态检索，且这些时长只是这台机器的少量样本。

`SessionStart` 的固定输出另测得：`startup` 6,760 B，`compact` 7,025 B；后者包含压缩后恢复提示。

| 四轮方案 | 计算出的 Hook 输出 | 相对每轮全量的减少 | 功能风险 |
|---|---:|---:|---|
| 每轮固定内容 + 每轮动态路由 | 42,872 B | 基线 | 当前行为 |
| 固定内容在第 1、4 轮；每轮动态路由 | 25,360 B | 40.8% | 固定提醒的跨轮保留未验证 |
| 固定内容只在第 1 轮；每轮动态路由 | 16,604 B | 61.3% | 固定提醒的跨轮保留未验证 |

动态路由不能照搬隔轮策略：根因分析轮返回 `systematic-debugging`，README 轮返回 `readme`，安装 Skill 轮返回创建/安装相关候选。若只在第 1 轮运行整个 Hook，后续提示拿不到与新任务匹配的推荐。

## 尚未证明的事

本实验未测出一次 Hook 附加内容在模型对话中实际保留多少轮，也未测真实输入 token、缓存或端到端模型延迟。独立 Codex CLI 测试会话的认证返回 401，无法运行四轮模型 A/B；官方 OpenAI Docs 页面在这台机器返回 403，也无法据此推断内部保留规则。因此 **61.3% 仅是 Hook 输出字节的理论削减，不是已实现的 token 或成本节约**。

下一步需要在可用的模型会话里做相同任务序列的 A/B：固定内容每轮注入与每四轮注入各运行多轮；动态路由两组都保持每轮；在第 2、3 轮切换任务，并单独测试恢复/压缩后首轮。记录真实输入与缓存 token、总延迟、动态 Skill 命中和固定规则遵守情况。只有证明后两项没有退化，才调整固定内容频率。当前生产频率保持不变。
