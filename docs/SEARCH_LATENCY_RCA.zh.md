# 搜索与路由延时：分层根因及修复

2026-10-20。本轮目标是减少实际延时，不以一次工具卡、配置上限或缓存命中冒充端到端性能。

## 1. 原61秒任务究竟慢在哪里

对已有真实事件重新计时：一次搜索请求为6,987毫秒；后续读页和页内查找共5,803毫秒；Hook区间合计3,108毫秒。事件观察窗口为59,757毫秒，另有43,859毫秒不处于已观测工具或Hook区间。原运行器从进程启动计为60,779毫秒，两个口径的起点不同，不能强行对齐成同一个数。

工具外时间包含启动、模型/提供方等待和回答输出，现有证据不能再细分为纯推理、网络或某一方的服务端排队。因此“搜索花61秒”和“开更多并发即可消除61秒”都不成立。已知网页任务中约8秒处于读页区间，约54秒处于工具和Hook之外；这些同样不证明54秒都是思考。

新增 `scripts/codex-latency.mjs` 依据真实started/completed事件记录搜索、读页、Hook和未归因区间；对重叠区间取并集，不相加虚增；缺失开始事件、未完成操作和合并成零时长的事件均显式保留限制。`test-codex-hook-runtime.mjs` 已接入此测量，不把task success当作延时达标。

## 2. 本地可修复的重复计算

直接连接本机已预热GraphToolCall进程：缓存命中约2.7毫秒，新问题约1,547毫秒。单独的提醒脚本约99毫秒，缓存命中的Skill路由约111毫秒，完整dispatcher约166毫秒。这是当次样本，不是分位数或长期保证。

cProfile在一次新查询中测得总计1.454秒，其中描述重排1.069秒，两个向量编码阶段合计1.143秒。库的`_boost_embedding_rerank`每次调用provider.encode_batch([query] + 前十候选描述)；原缓存仅在某个进程遇到相同描述之后才命中，四个进程各自填充，不能保证新问题不触发描述推理。

## 3. 已实施的修复边界

仍使用相同多语言模型、相同图、BM25/向量/图融合、候选池和重排公式，没有取消语义检索、减少候选或替换模型。

将首次已经计算出的描述向量保存到用户本机SQLite共享缓存，不让四个Worker和之后的重启各自重复推理。键包含描述全文、模型、固定revision和schema的哈希；数据按明确小端float32保存。保留描述-only向量，不拿原来包含工具名称、标签等的canonical向量冒充它，否则会改变重排含义。

模型、固定revision、schema或描述改变时不会命中旧键。仅当前图中真实描述可以持久化，用户问题向量只保留在内存；SQLite最多保留32,768条，超出时删除最早条目。缓存损坏明确报错，不静默跳过重排。动态问题向量仍按有界LRU缓存，不把整份技能正文或向量投入模型上下文。

缓存首次未命中仍需真实编码，不能宣传所有新描述都是毫秒级。SQLite采用WAL并由各进程自己的连接访问，图重新加载时明确关闭旧连接，不引入新服务。既有图文件和排序数据无需重新编码或扩容。

本轮试过“先预计算完整描述库再部署”，但首次构建触发20分钟部署超时，未产出新图，已撤回；严格新schema门槛也已撤回。最终实现不让部署等待全库描述计算，不把失败尝试计为成功优化。

最终版另在Windows预热时核对运行进程的代码SHA-256与磁盘文件，而不只比较图版本；修改代码但图不变时，同样通过受认证停止入口重启旧进程。缓存采用WAL/NORMAL，避免每次写入派生缓存都等待fsync；断电可能丢失最近缓存事务，届时重新计算，源图不受影响。这个取舍仅用于可重新生成的向量缓存，不用于用户记录或权威数据。依据：SQLite官方 `https://www.sqlite.org/pragma.html#pragma_synchronous`。

## 4. 依据与验收口径

直接核对本机固定版本graph-tool-call 0.46.0的retrieval/engine.py、embedding.py及tool_graph.py：描述重排的输入、float32相似度计算和metadata保存/恢复均有实际代码依据。查阅Python官方cProfile说明和Sentence Transformers语义搜索说明；外部检索在本轮没有返回可用正文，故不把未取得的网页当作引用支撑，结论以本机版本源码和真实测量为准。

缓存的机械测试覆盖跨实例共享、模型/revision/文本键隔离、用户查询不持久化、损坏拒绝，以及同一真实检索管线在缓存前后的排序和分数一致性。它不是全库所有问题质量不变的数学证明，仍须运行真实正例与硬负例。

实时外网搜索通过当前原生web工具完成，本轮没有改它的服务端、添加搜索账号或切换提供方。旧样本真实搜索约7秒；本地向量缓存优化不等于已经把这一段压到毫秒。更不能承诺包含大模型分析和原文核验的整个任务毫秒完成。

## 6. 最终实测与未解决项

本机部署完成且check返回changedFiles=0；四个检索进程就绪，内存运行代码SHA与磁盘一致。原图15,526个canonical向量全部复用，没有重新编码；77条方法论、9份Prompt、22个受管Skill保持一致。

组件对照中的相关新查询：修前1,546.7毫秒；首次改版742.5毫秒，最终版837.5毫秒。重复查询最终为2.1毫秒。重启后首次查询仍为1,718.7毫秒；不能把每种新问题、每种缓存状态说成同一性能。最终缓存命中的独立Skill脚本约85毫秒、dispatcher约159毫秒。以上是固定输入的单样本，不是分位数，也不等于端到端提速。

另一个独立Python进程加载真实图、复用持久缓存后，对同一基准查询观测到仅一批1条动态问题向量推理、0条静态描述推理；耗时829.3毫秒。118条持久记录已存在。这个实物证据证明跨进程描述复用确实发生，而不是只设置缓存开关。

真实质量测试10/10仍通过；其中部分未缓存查询耗时1.4–4.3秒，所以“不论何种输入都毫秒级”的目标没有达到。SQLite跨真实子进程读回、用户问题不落盘、模型/revision隔离、损坏拒绝、实际排序与分数一致、分层计时重叠/缺失事件、内存旧代码拒绝等测试通过；15项PR门禁再次通过。Mac原生完整安装未在本机Windows重跑，不宣称Mac/服务器同步通过。

以相同自然用户任务重新测试，未告诉模型合批或简短：总计105,734毫秒，搜索5,833毫秒、读页12,422毫秒、Hook合计1,245毫秒、另一次Skill文件读取192毫秒，未归因时间86,042毫秒。首次搜索确实合并3个查询；最终回答500个可见字符，仍未满足此前300字符标准。相较原60,779毫秒样本，这次整体更慢，不能以本地组件优化冒报端到端提速；查询条数、网页操作和模型输出轨迹也不同，不是受控性能对照。

新轨迹中，模型在有指定官方资料的API查证中额外读取discover-quality-references。该Skill描述包含宽泛的“recommendation / external evidence”，而正文是开放式质量发现并包含阶段边界；这是值得验证的误触发假设。但文件读取本身只有192毫秒，尚未做收窄触发后对照，不能将86秒全部归因于它，也没有在本轮擅自覆盖该非仓库受管的本机Skill。

因此本轮仅交付了局部重复计算修复、真实分层计时和运行代码校验；**实时外网搜索毫秒级、整体稳定提速、精简输出尚未解决**。没有换搜索提供方、降低模型或推理档位、减少原始方法论或虚构命中缓存的实时性。

最终本机证据：`.reports/router-latency-final.json`、`.reports/check-live-description-cache.py`、`.reports/skill-routing-quality.json`、`.reports/mac-profile-windows-validation.json`、`.reports/latency-final-natural/.reports/trusted-hook-live-result.json`及同目录事件日志。最终安装事务备份：用户`.codex/backups/portable-profile/20261020T084028Z/`；失败的全库预计算没有替换原图。SQLite为本机可再生成缓存，不提交Git。
