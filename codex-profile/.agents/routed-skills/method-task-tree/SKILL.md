# Task Tree Method

## Routing instruction

Apply every rule below when this Skill is selected. These are the user's original rules translated into English, not a rewritten summary. The nearest project `AGENTS.md` may add stricter prerequisites.

## User's original wording — English translation

- [TT01] This project uses `task-tree.md` in the repository root as the task state shared by all Agents.
- [TT02] When the `task_tree_*` MCP tools are available, prefer using them. Codex registers these tools through `[mcp_servers.task_tree]` in `~/.codex/config.toml`; Cursor registers them through the committed `.cursor/mcp.json`, which points to `llm-task-tree/mcp-server.mjs`. When the tools are available, use them instead of manually editing Markdown.
- [TT03] Use `task_tree_focus` to read the focus; use `task_tree_node` to read a single node.
- [TT04] When working with multiple Agents, use `task_tree_scope` to create or read the execution scope. The priority is “the user's latest request > this Agent's execution scope > the global `GraphState.Next`.” Only target nodes within the scope are execution targets, and only writable nodes within the scope may be modified; the global Current/Next remains the project view visible to humans.
- [TT05] uses `task_tree_write` for field-level writes. It creates a backup, runs compact gates, synchronizes workflow state, and refuses to modify `GraphState.Current/Next/NextPlan`, ensuring that focus remains under the user's control.
- [TT06] An Agent with execution scope must pass `scopeId`, or use the injected `TASK_TREE_EXECUTION_SCOPE`, and must not overwrite the Markdown of the entire tree. The server serially applies node patches based on the latest tree, so multiple Agents concurrently writing to different authorized nodes will not overwrite one another.
- [TT07] After each successful task tree or subtree write, only the actual persisted `changes` returned by the tool or API may be used to tell the user about every changed node and field in the form “old value → new value.” Do not infer the receipt from memory or requested fields; omit unchanged fields and protected fields.
- [TT08] `task_tree_chain` advances one step in a chain; `task_tree_flow_status` reports workflow drift; `task_tree_check_compact` runs compact gates; `task_tree_layout` rearranges the canvas; `task_tree_knowledge` searches the local index.
- [TT09] When the user wants to manipulate the task graph directly, use `task_tree_open` to embed a real UI (MCP Apps widget) in the chat, including dragging, editing, a flow view, and a knowledge panel; when the user only wants to view it, use `task_tree_render` to return an image. Both tools are for user viewing; use other tools when the model reads data.
- [TT10] `task_tree_server open` opens a UI on the user's desktop; use it when the host cannot render the widget.
- [TT11] If the tool call fails, fall back to the file rules below and explicitly tell the user.
- [TT12] `task-tree.md` is the current working graph, not an append-only history log; keep the history in `versions/`.
- [TT13] Before retaining a statement, apply the core-state deletion test: if removing it would not change the next action, method, current constraints, unresolved risks, or completion tests, move it to evidence, another tree, or delete it outright. When the task tree is noisy or exceeds the total-size gate, load `task-tree-core-state`.
- [TT14] Before taking action, read ROOT and the current phase's `Problem`, `Approach`, and `Metrics`, retain the goals explicitly stated by the user, and derive how the current node serves those goals. If the task tree and the user's latest request cannot support this connection, do not fabricate it. `CurrentResult` Directly state the verified current capabilities or evidence, the remaining gaps, and whether the relevant goals can currently be claimed as achieved; numbers are optional. Leave specific execution details in `NextIdea` and the evidence.
- [TT15] After completing each coherent unit of work, meaning an independently verifiable result, decision, failure, or blocker, write the measured state to the smallest affected node before starting the next unit; do not postpone all task tree maintenance until the end of the turn.
- [TT16] Replace or delete outdated content; do not add tombstone notes such as “deleted on...”.
- [TT17] Before adding text, first refine the touched nodes or edges: remove notes that are redundant, superseded, or meaningful only to the process.
- [TT18] Observe the hard limits: there may be only one `Problem`; `Approach` must retain only current content and contain no more than 4 bullet points; `CurrentResult` must state only one status relative to the goal, with no more than 3 verified facts and 500 characters; `RootCauseAnalysis` must contain no more than 2 sentences and 350 characters; there may be at most 2 cases; there may be only one executable `NextIdea`.
- [TT19] When cleaning up a large task tree, measure the byte count, line count, over-budget fields, and lines longer than 240 characters before and after the changes. Process the current path and the 8 to 15 most severely over-budget nodes; aim to reduce the text of the processed nodes by at least 25% and the number of long lines by at least 30%, unless facts that must be preserved prevent meeting those targets.
- [TT20] Parent nodes are indexes, not storage bins: if a node has child nodes or formula nodes, retain only the current conclusion, 2 to 3 key numbers, and references to child nodes or files.
- [TT21] If old text conflicts with the current method, rewrite or delete the old text; do not allow both the old and new methods to remain valid simultaneously.
- [TT22] Use concise Chinese by default for node semantic fields. Retain only familiar terms such as `LLM`, `token`, and `API`, as well as exact names, IDs, paths, and URLs; complex English domain terms should be translated into Chinese or moved into evidence.
- [TT23] Do not paste code, JSON, commands, formulas, raw data rows, stack traces, or logs into nodes. This rule overrides earlier provisions for inline examples in the frozen detailed protocol.
- [TT24] `Input` and `Output` use brief Chinese evidence descriptions and may include actual file paths; raw samples should be placed in previewable evidence files.
- [TT25] Add a new node only when a subproblem is genuinely independent and has distinct inputs, outputs, and metrics.
- [TT26] If changes to the method or sequence affect the execution order, also update `scripts/project.json` or `scripts/run.json`; changing only `CurrentResult` usually does not require this.
- [TT27] When saving the task tree or running postflight, deterministic workflow state is automatically synchronized and minimal step evidence is created; the Agent must still resolve missing or stale sections and intentional sequence changes.
- [TT28] Do not over-refine: preserve currently measured facts, unresolved risks, user decisions, and current constraints.
- [TT29] Each task reads only the task-tree context by default: if an Agent execution scope exists, execute only the nodes assigned to it and treat `GraphState.Current/Next` as background; otherwise, read `task-tree.md` and use `GraphState.Current`, `GraphState.Next`, and the Next node's `NextIdea`. `NextPlan` is a potentially stale user memo and must never be executed. This advisory-only policy overrides legacy wording retained in the frozen complete protocol for audit compatibility that permits executing NextPlan. Also read ROOT's `Problem`, `Approach`, and `Metrics`; verify completion claims through evidence, and do not treat plans, filenames, screenshots, or intended designs as proof.
- [TT30] Treat the task tree as the authoritative state; chat history and isolated files may only serve as evidence.
- [TT31] Unless the current turn will modify the task tree or the execution workflow, do not read `llm-task-tree/AGENTS.task-tree.md`, task-tree Skills, or `scripts/README.md`.
- [TT32] When you are about to modify the task tree, meaning write, create, or repair `task-tree.md`, `subtrees/*.md`, nodes, edges, or GraphState, you must first read the following completely and in order before any write in the same turn: `llm-task-tree/AGENTS.task-tree.md`, `llm-task-tree/AGENTS.node-writing.md`, `llm-task-tree/skills/task-tree-grill/SKILL.md`, `llm-task-tree/skills/task-tree-grill/references/schema-template.md`.
- [TT33] Before manually modifying the task tree, back up `task-tree.md` to `versions/<timestamp>_<原因>.md`; see Section 7 of the protocol. The file order must be “all nodes → `# GraphState` → `# Edges`”. The corresponding rule for Cursor is `.cursor/rules/llm-task-tree-edit.mdc`.
- [TT34] When you are about to modify the execution flow, that is, write to `scripts/project.json` or `scripts/run.json`, or call `PUT /api/flow-script`, before any write in the same turn, you must first read the following completely and in order: `scripts/README.md`, which is the authoritative execution-flow specification for the schema, block types, when to modify or not modify, and saving and backups; the current `scripts/project.json`, and if modifying run mode, also read `scripts/run.json`; inspect `task-tree.md` and the relevant `subtrees/*.md` to confirm valid `nodeId` values.
- [TT35] Before modifying the execution flow, back it up to `scripts/versions/project/` or `scripts/versions/run/`; you may also use the API, which creates a backup by default. Execution order resides in scripts, not in node ID ordering or graph layout. The corresponding rule for Cursor is `.cursor/rules/llm-task-tree-flow-edit.mdc`; for the complete gate, see Section 1c of `llm-task-tree/AGENTS.task-tree.md`.
- [TT36] Only if the current turn modified the task tree or execution workflow, apply the following finalization rules: update the smallest relevant node(s) and/or `blocks`; for task-tree writes, report each node or field difference actually persisted as “old value → new value,” based on the write result.
- [TT37] When writing a node's `Input` and `Output`, use brief descriptions in Chinese and optionally include paths; do not paste raw samples or code.
- [TT38] If the execution workflow changes, record the change in the `Notes` of the affected node.
- [TT39] If any task tree or subtree changes, run `powershell -NoProfile -ExecutionPolicy Bypass -File llm-task-tree/check-tree-compact.ps1 <changed tree paths>`. A nonzero exit code blocks any completion claim: each reported over-budget field must be semantically rewritten, and the command must be rerun until it passes; facts must never be mechanically truncated. Codex Stop Hook automatically enforces this check; other Agents must run it explicitly.
- [TT40] If no task tree exists yet, create one from `llm-task-tree/templates/task-tree.starter.md`, or run `task-tree-grill`; the task-tree path specified above must be read first.
- [TT41] The entry point for the task graph UI is `llm-task-tree/打开任务图.cmd`; within it, “Relationship Graph | Execution Flow” corresponds to `scripts/project.json` and `scripts/run.json`.
