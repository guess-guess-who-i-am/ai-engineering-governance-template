# Task Tree Method

## Routing instruction

Apply every rule below when this Skill is selected. These are the user's original rules translated into English, not a rewritten summary. The nearest project `AGENTS.md` may add stricter prerequisites.

## User's original wording — English translation

- [TT01] This project uses `task-tree.md` in the repository root as the shared task state for all Agents.
- [TT02] When `task_tree_*` MCP tools are available, prioritize using them. Codex registers these tools through `[mcp_servers.task_tree]` in `~/.codex/config.toml`; Cursor registers them through the committed `.cursor/mcp.json`, which points to `llm-task-tree/mcp-server.mjs`. When tools are available, use the tools instead of manually editing Markdown.
- [TT03] Use `task_tree_focus` to read the focus; use `task_tree_node` to read a single node.
- [TT04] When working with multiple Agents, use `task_tree_scope` to create or read the execution scope. The priority is “the user's latest request > this Agent's execution scope > global `GraphState.Next`”. Only target nodes within the scope are execution targets, and only writable nodes within the scope may be modified; global Current/Next remain the project view seen by humans.
- [TT05] uses `task_tree_write` for field-level writes. It backs up, runs the compact gate, synchronizes process status, and refuses to modify `GraphState.Current/Next/NextPlan`, keeping the focus determined by the user.
- [TT06] Agents with an execution scope must pass `scopeId`, or use the injected `TASK_TREE_EXECUTION_SCOPE`, and must not overwrite the Markdown of the entire tree. The server serially applies node patches based on the latest tree, so multiple Agents concurrently writing different authorized nodes will not overwrite one another.
- [TT07] After each successful task-tree or subtree write, based only on the actual persisted `changes` returned by the tool or API, tell the user each changed node and field as “old value → new value”. Do not infer the receipt from memory or request fields; omit unchanged fields and protected fields.
- [TT08] `task_tree_chain` moves forward one chained step; `task_tree_flow_status` reports process drift; `task_tree_check_compact` runs the compact gate; `task_tree_layout` rearranges the canvas; `task_tree_knowledge` searches the local index.
- [TT09] When the user wants to operate the task graph directly, use `task_tree_open` to embed a real UI (MCP Apps widget) in the chat, including dragging, editing, flow view, and knowledge panel; when the user only wants to view, use `task_tree_render` to return an image. Both tools serve the user for viewing; when the model reads data, use other tools.
- [TT10] `task_tree_server open` will pop up a UI on the user's desktop; use it when the host cannot render the widget.
- [TT11] If a tool call fails, fall back to the file rules below and clearly tell the user.
- [TT12] `task-tree.md` is the current working graph, not an append-only historical log; history is stored in `versions/`.
- [TT13] Before retaining a statement, apply the core-state deletion test: if deleting it would not change the next action, method, current constraints, unresolved risks, or completion tests, move it into evidence, another tree, or delete it directly. When the task tree is noisy or exceeds the total-size gate, load `task-tree-core-state`.
- [TT14] Before acting, read ROOT and the current phase's `Problem`, `Approach`, and `Metrics`, retain the goals explicitly stated by the user, and infer how the current node serves those goals. If the task tree and the user's latest request cannot support such a connection, do not invent one.`CurrentResult` State directly the currently verified capabilities or evidence, the remaining gaps, and whether attainment of the relevant goals can currently be claimed; numbers are optional. Keep specific execution details in `NextIdea` and the evidence.
- [TT15] After completing each coherent work unit—that is, an independently verifiable result, decision, failure, or blocker—write the measured state into the smallest affected node before starting the next unit; do not defer maintaining the entire task tree until the end of the turn.
- [TT16] Replace or delete obsolete content; do not add tombstone notes such as “deleted on ...”.
- [TT17] Before adding text, first refine the affected nodes or edges: remove notes that are repetitive, superseded, or serve only a process purpose.
- [TT18] Follow hard budgets: there may be only one `Problem`; `Approach` retain only current content and no more than 4 bullet points; `CurrentResult` write only one status relative to the goals, with no more than 3 verified facts and 500 characters; `RootCauseAnalysis` no more than 2 sentences and 350 characters; at most 2 cases; only one executable `NextIdea`.
- [TT19] When cleaning up a large task tree, measure the byte count, line count, over-budget fields, and long lines exceeding 240 characters before and after modification. Handle the current path and the 8 to 15 nodes with the most severe budget overruns; the target is to reduce the text of handled nodes by at least 25% and long lines by at least 30%, unless facts that must be retained prevent achieving that target.
- [TT20] A parent node is an index, not a storage box: if a node has child nodes or formula nodes, retain only the current conclusion, 2 to 3 key figures, and references to child nodes or files.
- [TT21] If old text conflicts with the current method, rewrite or delete the old text; do not let both the old and new methods remain valid simultaneously.
- [TT22] Node semantic fields default to concise Chinese. Retain only `LLM`, `token`, `API`, and other familiar terms, as well as exact names, IDs, paths, and URLs; complex English domain terminology should be translated into Chinese or moved into evidence.
- [TT23] Do not paste code, JSON, commands, formulas, raw data lines, stack traces, or logs into nodes. This rule overrides the earlier inline example provisions in the frozen detailed protocol.
- [TT24] `Input` and `Output` use brief Chinese evidence descriptions, and may append actual file paths; raw samples should be placed in previewable evidence files.
- [TT25] Add a node only when a subproblem is truly independent and has different inputs, outputs, and metrics.
- [TT26] If changing the method or sequence affects execution order, also update `scripts/project.json` or `scripts/run.json`; modifying only `CurrentResult` usually does not require this.
- [TT27] When saving the task tree or executing postflight, deterministic process state is automatically synchronized and minimal step evidence is created; Agent must still resolve missing or stale blocks and intentional sequence changes.
- [TT28] Do not over-refine: retain currently measured facts, unresolved risks, user decisions, and current constraints.
- [TT29] By default, each task reads only task-tree context: if an Agent execution scope exists, execute only the nodes assigned to it, treating `GraphState.Current/Next` as background; otherwise read `task-tree.md`, and use `GraphState.Current`, `GraphState.Next`, and the Next node's `NextIdea`. `NextPlan` is a potentially stale user memo and must never be executed. This advisory-only strategy overrides the old wording in the frozen complete protocol that allows executing NextPlan and was retained for audit compatibility. Also read ROOT's `Problem`, `Approach`, and `Metrics`; verify completion claims through evidence, and do not treat plans, filenames, screenshots, or expected designs as proof.
- [TT30] Treat the task tree as authoritative state; chat history and isolated files can serve only as evidence.
- [TT31] Unless the current turn will modify the task tree or modify the execution flow, do not read `llm-task-tree/AGENTS.task-tree.md`, task-tree Skills, or `scripts/README.md`.
- [TT32] When you are about to modify the task tree—that is, write, create, or repair `task-tree.md`, `subtrees/*.md`, nodes, edges, or GraphState—you must, before any write in the same turn, completely read in order: `llm-task-tree/AGENTS.task-tree.md`, `llm-task-tree/AGENTS.node-writing.md`, `llm-task-tree/skills/task-tree-grill/SKILL.md`, `llm-task-tree/skills/task-tree-grill/references/schema-template.md`.
- [TT33] Before manually modifying the task tree, back up `task-tree.md` to `versions/<timestamp>_<原因>.md`; see Section 7 of the protocol. File order must be “all nodes → `# GraphState` → `# Edges`”. The Cursor counterpart rule is `.cursor/rules/llm-task-tree-edit.mdc`.
- [TT34] When you are about to modify the execution flow—that is, write to `scripts/project.json`, `scripts/run.json`, or call `PUT /api/flow-script`—you must, before any write in the same turn, fully read the following in order: `scripts/README.md`, which is the authoritative execution-flow wording for the schema, block types, when to modify or not modify, saving, and backups; the current `scripts/project.json`; and, if modifying the run mode, also read `scripts/run.json`; browse `task-tree.md` and the related `subtrees/*.md` to confirm valid `nodeId` values.
- [TT35] Before modifying the execution flow, back up to `scripts/versions/project/` or `scripts/versions/run/`; you may also use the API that backs up by default. The execution order exists in scripts, not in node ID sorting or graph layout. The corresponding Cursor rule is `.cursor/rules/llm-task-tree-flow-edit.mdc`; see the complete gate in `llm-task-tree/AGENTS.task-tree.md` Section 1c.
- [TT36] Apply the following wrap-up rules only when the current turn modified the task tree or execution flow: update the smallest relevant nodes and/or `blocks`; for task-tree writes, based on the write result, report each actually persisted node or field difference as “old value → new value”.
- [TT37] When writing a node’s `Input` and `Output`, use a brief Chinese description and optionally include a path; do not paste the original sample or code.
- [TT38] If the execution flow changes, record the change in `Notes` of the affected node.
- [TT39] If any task tree or subtree changes, run `powershell -NoProfile -ExecutionPolicy Bypass -File llm-task-tree/check-tree-compact.ps1 <changed tree paths>`. A nonzero exit code blocks a completion claim: every reported over-budget field must be rewritten semantically, and the check must be rerun until it passes; never mechanically truncate facts. The Codex Stop Hook automatically enforces this check; other Agents must run it explicitly.
- [TT40] If there is no task tree yet, create one from `llm-task-tree/templates/task-tree.starter.md`, or run `task-tree-grill`; you must first read the task-tree path specified above.
- [TT41] The entry point for the task graph UI is `llm-task-tree/打开任务图.cmd`; within it, “Relationship Graph | Execution Flow” corresponds to `scripts/project.json` and `scripts/run.json`.
