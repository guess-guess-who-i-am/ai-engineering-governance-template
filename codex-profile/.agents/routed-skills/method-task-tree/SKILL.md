# Task Tree Method

## Routing instruction

Apply every rule below when this Skill is selected. These are the user's original rules translated into English, not a rewritten summary. The nearest project `AGENTS.md` may add stricter prerequisites.

## User's original wording — English translation

- [TT01] This project uses `task-tree.md` in the repository root directory as the task state shared by all Agents.
- [TT02] When the `task_tree_*` MCP tools are available, prefer using them. Codex registers these tools through `[mcp_servers.task_tree]` in `~/.codex/config.toml`; Cursor registers them through the committed `.cursor/mcp.json`, which points to `llm-task-tree/mcp-server.mjs`. When the tools are present, use the tools instead of manually editing Markdown.
- [TT03] Use `task_tree_focus` to read the focus; use `task_tree_node` to read a single node.
- [TT04] When multiple Agents are working, use `task_tree_scope` to create or read the execution scope. The priority is “the user's latest request > this Agent's execution scope > global `GraphState.Next`”. Only target nodes within the scope are execution targets, and only writable nodes within the scope may be modified; global Current/Next remains the project view that humans see.
- [TT05] Use `task_tree_write` for field-level writes. It creates backups, runs the compactness gate, synchronizes workflow state, and refuses to modify `GraphState.Current/Next/NextPlan`, leaving the focus for the user to decide.
- [TT06] An Agent with an execution scope must pass in `scopeId` or use the injected `TASK_TREE_EXECUTION_SCOPE`, and must not overwrite the entire tree's Markdown. The server applies node patches serially against the latest tree, so multiple Agents concurrently writing to different authorized nodes will not overwrite one another.
- [TT07] After each successful write to a task tree or subtree, report every changed node and field to the user as “old value → new value” based solely on the actual persisted `changes` returned by the tool or API. Do not infer the write receipt from memory or requested fields; omit unchanged fields and protected fields.
- [TT08] `task_tree_chain` advances one step in a chain; `task_tree_flow_status` reports workflow drift; `task_tree_check_compact` runs the compactness gate; `task_tree_layout` rearranges the canvas; `task_tree_knowledge` searches the local index.
- [TT09] When the user wants to interact directly with the task graph, use `task_tree_open` to embed a real UI (MCP Apps widget) in the chat, including dragging, editing, a flow view, and a knowledge panel; when the user only wants to view it, use `task_tree_render` to return an image. Both tools serve user viewing; use other tools when the model reads data.
- [TT10] `task_tree_server open` opens a UI on the user's desktop; use it when the host cannot render widgets.
- [TT11] If a tool call fails, fall back to the file rules below and explicitly tell the user.
- [TT12] `task-tree.md` is the current working graph, not an append-only historical log; put history in `versions/`.
- [TT13] Before retaining a statement, apply the core-state deletion test: if deleting it would not change the next action, method, current constraints, unresolved risks, or completion tests, move it into evidence or another tree, or delete it outright. When the task tree is noisy or exceeds the total-size gate, load `task-tree-core-state`.
- [TT14] Before taking action, read `Problem`, `Approach`, and `Metrics` for ROOT and the current phase, retain the goals explicitly stated by the user, and infer how the current node serves those goals. If the task tree and the user's latest request do not support this connection, do not invent it. `CurrentResult` must directly state the verified current capabilities or evidence, the remaining gaps, and whether the relevant goals can currently be claimed to have been achieved; numbers are optional. Keep specific execution details in `NextIdea` and the evidence.
- [TT15] Whenever a coherent unit of work is completed—that is, an independently verifiable result, decision, failure, or blocker—write the measured state into the smallest affected node before starting the next unit; do not defer all task-tree maintenance until the end of the turn.
- [TT16] Replace or delete outdated content; do not add tombstone notes such as “deleted on…”.
- [TT17] Before adding text, first refine the nodes or edges being touched: remove notes that are redundant, superseded, or meaningful only as process records.
- [TT18] Observe the hard budgets: there may be only one `Problem`; `Approach` must retain only current content and contain no more than 4 bullet points; `CurrentResult` must state only one status relative to the goals, with no more than 3 verified facts and 500 characters; `RootCauseAnalysis` must contain no more than 2 sentences and 350 characters; there may be at most 2 cases; there may be only one executable `NextIdea`.
- [TT19] When cleaning up a large task tree, measure byte counts, line counts, over-budget fields, and long lines exceeding 240 characters before and after the changes. Process the current path and the 8 to 15 nodes with the most severe budget overruns; aim to reduce the text in the processed nodes by at least 25% and the number of long lines by at least 30%, unless facts that must be retained prevent these targets from being met.
- [TT20] Parent nodes are indexes, not storage bins: if a node has child nodes or formula nodes, retain only the current conclusion, 2 to 3 key numbers, and references to child nodes or files.
- [TT21] If old text conflicts with the current method, rewrite or delete the old text; do not leave both the old and new methods in effect simultaneously.
- [TT22] Node semantic fields use concise Chinese by default. Retain only familiar terms such as `LLM`, `token`, and `API`, along with exact names, IDs, paths, and URLs; complex English domain terms should be translated into Chinese or moved into evidence.
- [TT23] Do not paste code, JSON, commands, formulas, raw data rows, stack traces, or logs into nodes. This rule overrides the earlier inline-example provisions in the frozen detailed protocol.
- [TT24] `Input` and `Output` use brief Chinese evidence descriptions and may include actual file paths; raw samples should be placed in previewable evidence files.
- [TT25] Add a node only when a subproblem is genuinely independent, with different inputs, outputs, and metrics.
- [TT26] If changes to methods or ordering affect the execution order, also update `scripts/project.json` or `scripts/run.json`; modifying only `CurrentResult` usually does not require this.
- [TT27] Saving the task tree or running postflight automatically synchronizes deterministic workflow state and creates minimal step evidence; the Agent must still resolve missing or outdated blocks and intentional ordering changes.
- [TT28] Do not over-condense: retain currently measured facts, unresolved risks, user decisions, and current constraints.
- [TT29] For each task, read only the task-tree context by default: if an Agent execution scope exists, execute only the nodes assigned to it and treat `GraphState.Current/Next` as background; otherwise, read `task-tree.md` and use `GraphState.Current`, `GraphState.Next`, and the Next node's `NextIdea`. `NextPlan` is a potentially outdated user memo and must never be executed. This advisory-only policy overrides the legacy wording permitting NextPlan execution retained in the frozen full protocol for audit compatibility. Also read ROOT's `Problem`, `Approach`, and `Metrics`; verify claims of completion using evidence, and do not treat plans, filenames, screenshots, or intended designs as proof.
- [TT30] Treat the task tree as the authoritative state; chat history and isolated files may serve only as evidence.
- [TT31] Unless the current turn will modify the task tree or the execution workflow, do not read `llm-task-tree/AGENTS.task-tree.md`, task tree Skills, or `scripts/README.md`.
- [TT32] When you are about to modify the task tree, meaning writing, creating, or repairing `task-tree.md`, `subtrees/*.md`, nodes, edges, or GraphState, you must read the following in full and in this order before any write in the same turn: `llm-task-tree/AGENTS.task-tree.md`, `llm-task-tree/AGENTS.node-writing.md`, `llm-task-tree/skills/task-tree-grill/SKILL.md`, `llm-task-tree/skills/task-tree-grill/references/schema-template.md`.
- [TT33] Before manually modifying the task tree, back up `task-tree.md` to `versions/<timestamp>_<原因>.md`, see Section 7 of the protocol; the file order must be “all nodes → `# GraphState` → `# Edges`”. The corresponding Cursor rule is `.cursor/rules/llm-task-tree-edit.mdc`.
- [TT34] When you are about to modify the execution workflow, meaning write to `scripts/project.json` or `scripts/run.json` or call `PUT /api/flow-script`, before any writes in the same turn, you must read the following in full and in order: `scripts/README.md`, which is the authoritative specification for the execution workflow's schema, block types, when to modify or not modify, saving, and backups; the current `scripts/project.json`, and, if modifying run mode, also read `scripts/run.json`; browse `task-tree.md` and the relevant `subtrees/*.md` to confirm valid `nodeId` values.
- [TT35] Before modifying the execution workflow, back it up to `scripts/versions/project/` or `scripts/versions/run/`; you may also use an API that creates backups by default. Execution order resides in scripts, not in node ID ordering or graph layout. The corresponding rule for Cursor is `.cursor/rules/llm-task-tree-flow-edit.mdc`; for the complete gate, see Section 1c of `llm-task-tree/AGENTS.task-tree.md`.
- [TT36] Execute the following wrap-up rules only if the current turn modified the task tree or execution workflow: update the smallest relevant node and/or `blocks`; for task tree writes, report each node or field difference actually persisted to disk as “old value → new value” based on the write results.
- [TT37] When writing a node’s `Input` and `Output`, use brief explanations in Chinese and optionally include paths; do not paste raw samples or code.
- [TT38] If the execution workflow changes, record the change in the affected node’s `Notes`.
- [TT39] If any task tree or subtree changes, run `powershell -NoProfile -ExecutionPolicy Bypass -File llm-task-tree/check-tree-compact.ps1 <changed tree paths>`. A nonzero exit code blocks completion claims: you must rewrite each reported over-budget field according to its meaning and rerun until the check passes; never mechanically truncate facts. The Codex Stop Hook automatically enforces this check; other Agents must run it explicitly.
- [TT40] If there is no task tree yet, create one from `llm-task-tree/templates/task-tree.starter.md`, or run `task-tree-grill`; you must first read the task tree path specified above.
- [TT41] The entry point for the task graph UI is `llm-task-tree/打开任务图.cmd`; within it, “Relationship Graph | Execution Flow” corresponds to `scripts/project.json` and `scripts/run.json`.
