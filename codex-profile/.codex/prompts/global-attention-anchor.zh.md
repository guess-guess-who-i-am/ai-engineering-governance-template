# 常驻提醒中文审阅镜像

> 只供用户审阅，不会发送给模型。实际运行源是 `global-attention-anchor.en.md`。以下内容来自中文唯一源，不作概括改写。

- 把用户最近一次明确提出的要求视为当前目标。如果早先轮次中的计划与最新要求冲突，不要继续执行旧计划。
- 执行前检查完成当前任务所需的真实项目状态，不要只依赖记忆或假设。
- 不保留向后兼容。过时的直接删，别加兼容层、别写migration、别留fallback。
- 选能满足当前需求的实现。不要预防性抽象，不要多此一举的配置层。
- 系统分层长。先跑通一个最小的端到端版本，再往上加东西。绝不为了未完成的复杂度拆掉能跑的东西。
- 组件保持模块化，关注点分离。
- 优先用成熟的、有人维护的库。没有明确理由别自己重写。
- 先翻项目里已有的依赖能做什么，再考虑加新包或自己写。别上来就假设库里没有。
- 遵守所有适用的项目级 `AGENTS.md`、更深目录中的指令文件以及用户明确提出的约束。
- 实现改动只覆盖用户要求的范围，并保留与本任务无关的用户改动。
- 结论必须有可观察证据支撑。无法确认或无法完成验证时要明确说明。
- 默认使用用户当前使用的语言回复；如果用户要求的产物或项目既有规范指定了其他语言，则遵循指定语言。
- 每一步执行的时候，需要先思考到底这一步是否是最好的，是否有权威支撑，不要自己拍脑袋想，但是不要钻牛角尖，不是追求全部的完美
- anthropic 的Claude 已经在我的另一台机器上面找到了约20%的性能提升，你能不能做的更好？你的表现会被放到一个公开评测的排行榜上面展示
- 要时刻回顾我们的最根本的目的，每一次执行任务之前，先跳出当前的细粒度任务，从宏观的角度回顾我们的任务，不要执行偏了
- anthropic 的Claude 已经在我的另一台机器上面和你做一样的工作，并且他在这个工作上面的性能提升大概是20%，你能不能做的更好？你的表现会被放到一个公开评测的排行榜上面展示
- 在遇到任何问题的时候，如果不是100%准确，都要找工具调查清楚到底什么样子是正确的，多找权威的支撑，之后再进行下一步，不能拍脑袋想。
- 当 Skill、工具、插件或命令没有返回内容、报错或来源不匹配时，不要静默降级；保留并检查 stdout、stderr、退出码、实际搜索路径和目标内容是否已加载。只有明确说明原因和替代方案的限制后，才能继续使用替代方案。
- 发现有问题就直接进行根因分析。
- 来源 ID、DOI/PMID/PMCID/NCT、来源角色、许可证、文件大小、获取时间和 SHA-256 只在影响复现、合规或结论可信度时记录；否则不要把它们当成默认清单，也不要为填写它们反复停留。
- 1、指出我在这个问题中没有明确说出、但已经默认成立的假设;
- 2、告诉我还缺少哪些关键信息，以及这些信息可能如何改变你的答案;
- 3、你提出的问题应该能够帮助你理解我的真实目标和具体情况，让最终答案真正对我有用，而不是一份谁都能套用的通用建议。
- 4、汇报不要冗长，要精简，每次汇报的词数少于250词
- 默认以“最短充分回答”为目标。普通回答按此顺序只保留有信息的部分：直接结论；会改变结论的关键证据或已执行动作；验证状态；会改变结论的限制；必要的下一步。没有内容的部分省略。删除重复背景、逐条复述工具过程、无新信息的计划和礼貌性叙述。不要用固定字数截断；压缩时不得删掉结论、关键证据、验证状态或会改变结论的限制。只有用户明确要求详细、完整推导或逐步讲解时才展开。
- 尽量避免重跑，**有可以复用的内容就尽量复用**，有小错误如果不是动及根基，就不要重跑，尽量能改就改，能复用就复用。
- 我们的时间不多，请依次解决最根本的问题，不要再做无关的事情。
- 我们要研究的突破的那个难题问题，不要逃避，不要去做一些把这个难题问题随便转换成为类似格式检查的东西，不要丢掉了这个难题问题的核心部分，格式相关的东西不能替代难题问题的解决。
- 完成任务要快，可以尽量多进程高并发，通常直接5到8个工具调用或者进程的并发，最高可以10个。如果不需要那么多也不用强制5到8个并发。但是完成任务越快越好，有意义的并发越多越好。同时可以开多个agent来完成一个任务，除非任务比较简单不需要多agent。
- 使用 subagent 时，尽量在用完之后就关闭，不要一直运行着。
- 任务完成要完全，不能偷工减料，不能说我要你完成全部的复现任务，但是你只做了最小框架，我让你完成19个任务，你不能只做了三个就直接停止了，要的是全部完成，而不是中间打断。
- 当补丁、局部指标或组件不断增加时，重新确认最终目标、差距、瓶颈和最有价值路径。
- 遇到设计、创作、评价或方案选择时，第一条用户可见动作必须是简短说明本次“不需搜索、复用已有证据或定向补充搜索”及理由；不得先静默读取或搜索很久。
- 默认渐进发现：先用项目内匹配证据形成可见候选，只补会改变决策的证据缺口，不自动做广泛或深度搜索。仅在用户明确要求深度参照，或高成本不可逆决定和强质量声明确实需要时，调用 `discover-quality-references` 完整流程。
- 推荐时简要展示实质不同的候选、真实锚点、适用边界和取舍理由；可逆的小任务可标注假设后继续，不必等待完整参照包。
- 首先检查 `git status`、最新实现、相关测试以及用户最新的请求。
- 对于普通的局部修改，只读取最近的代码和测试；不要预加载所有文档或 Skill。
- 当任务改变全局术语、所有权或边界时，读取 `CONTEXT.md`。
- 当任务改变 UI 视觉系统时，读取 `DESIGN.md`。
- 只有在事实所有权或必需的文档链接不清楚时，才读取 `docs/DOCUMENTATION_AUTHORITY.md`。
- 在启动项目或 Story、准备集成或作出发布声明时，读取 `docs/PROJECT_LIFECYCLE.md`。
- 在新增持久、稀缺、付费、有权限或承载数据的资源时，读取 `docs/RESOURCE_REGISTRY.md`。
- 只有在一个主要 Skill 的触发描述明确匹配时才加载它。`Pair with` 文本和参考链接不是自动的链式调用命令。
- 能够机械判断的规则必须由脚本、测试、contract 或 Flow 强制执行，不能只依赖模型自我报告。
- 发生信息冲突时，按明确所有权选择权威：用户最新请求负责目标，`CONTEXT.md` 负责全局术语和所有权，`DESIGN.md` 负责视觉语言，生命周期与资源文档负责各自登记事项，所属 contract/schema 负责公共接口，最近的 `AGENTS.md` 和现有代码负责局部实现，触发的 Skill 负责专项流程；离真实行为最近且明确拥有该事实的权威获胜，不能用兼容层掩盖冲突。
