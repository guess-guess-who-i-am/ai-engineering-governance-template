Context architecture

规则不是越多越好，而是要在正确时刻出现。

稳定约束常驻，领域语义按项目读取，专项方法按触发加载，能机械判断的要求落进脚本和 CI。

  1. 01

    常驻规则

    AGENTS.md 只保留跨任务不变量、权威路由与验证预算。

  2. 02

    项目上下文

    CONTEXT.md 和 DESIGN.md 分别拥有领域语义与视觉语言。

  3. 03

    按需 Skills

    触发描述负责“如果……那么”，正文只在任务匹配时加载。

  4. 04

    确定性执行

    脚本、Schema、测试和 Flow 承担可重复判断，不依赖模型记忆。

  5. 05

    证据与修复

    质量报告生成稳定 Finding，按优先级、责任人与生命周期闭环。

Triggered workflows

一个任务，一个主 Skill。

每个 Skill 都有明确触发与非触发边界，避免一次注入整套方法论。

定义

构建前澄清

只对高影响歧义冻结目标、边界和验收证据。

诊断

系统化调试

沿信息流寻找第一个偏差，以可证伪实验定位原因。

修复

TDD 修复回归

先留下失败证据，再做最小修复和相邻回归验证。

契约

契约演进

同步生产者、消费者、失败语义与端到端证据。

领域

项目领域建模

统一术语、边界、不变量和公共接口所有权。

界面

设计界面实现

依据视觉系统实现响应式、可访问的真实界面。

测试

建立测试体系

把用户故事映射到功能、性能、安全和发布证据。

审查

审查项目改动

从行为风险和证据充分性报告可执行 Finding。

治理

审查治理体系

检查规则、Skills、脚本、CI 和文档能否形成闭环。

验证

完成前验证

让完成声明对应真实消费者和当前输入的证据。

交付

编写 PR 说明

依据真实 diff、测试、风险和回滚信息生成说明。

启动

启动新项目

逐项冻结 brief，生成独立、默认私有且可治理的仓库。

Quality and remediation

绿色不是终点，失败也必须能被管理。

用户故事定义可观察结果，分层门禁产生证据，失败进入稳定 Finding，而不是消失在 CI 日志里。

  1. 用户故事US / AC
  2. 分层门禁PR / release / nightly
  3. 结构化报告gate + evidence
  4. Finding 闭环owner + status + issue
P0

秘密泄漏、可利用安全问题、数据破坏或系统不可用。

P1

核心旅程、公共契约或发布证据的重大回归。

P2

影响明确但可绕行，进入近期修复排期。

P3

体验、清晰度或维护性优化。

Explicit boundary

治理模板不假装是 Agent Runtime。
